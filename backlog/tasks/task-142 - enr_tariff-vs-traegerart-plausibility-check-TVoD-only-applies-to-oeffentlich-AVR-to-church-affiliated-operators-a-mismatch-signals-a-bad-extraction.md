## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
classify.enrich_description() regex-extracts enr_tariff from posting text (patterns.json TARIFF list). Some tariff schemes are legally/structurally tied to operator type: TVoeD is public-sector (traegerart=oeffentlich), AVR Caritas/Diakonie apply to church-affiliated (freigemeinnuetzig) operators specifically, Haustarif is private (privat). A posting whose extracted enr_tariff contradicts its clinic's traegerart (e.g. TVoeD on a privat clinic) likely means the regex matched something that wasn't actually the posting's own tariff (a quoted comparison, a footnote, boilerplate).
<!-- SECTION:DESCRIPTION:END -->

AC#3 -- DECISION: NOT implementing the blanket guard as literally specified ("don't trust enr_tariff when it contradicts traegerart"). Evidence: 13/15 sampled disagreements (86.7%), and by extension most of the 51 measured mismatches, are legitimate -- real, correctly-extracted statements of the posting's own actual or voluntary pay basis (private clinics referencing TVöD as a benchmark is itself a real, recurring, multi-employer practice; AMEOS retaining AVR Caritas after privatization; independent Haustarif agreements at gGmbH subsidiaries and BRK). A blanket "distrust on traegerart mismatch" guard would incorrectly suppress or flag ~44 good extractions to catch ~7 genuine bugs -- a bad trade, and exactly the outcome the task's own framing warned against ("don't assume every disagreement is a bug").

INSTEAD implemented the narrower, root-caused fix the investigation actually found: pflege_jobs/classify.py::enrich_description()'s tariff selection now skips a matched tariff name when it sits immediately next to a comparison phrase ("angelehnt an", "orientiert an", "in Anlehnung an", "über dem Tarif der/des", "vergleichbar mit", "analog zu/zum/zur") -- new module-level _TARIFF_CMP_PRE/_TARIFF_CMP_POST regexes -- and falls through to the next candidate in patterns.json's own declared TARIFF list order (unchanged otherwise: specific AVR variants still beat the generic "AVR (unspecified)" catch-all by list order, not text position). If every match in a description happens to be comparison-adjacent (not observed in the live data), it falls back to the first list-order match rather than losing the field to None.

IMPORTANT CORRECTION DURING IMPLEMENTATION: my first attempt used pure "earliest text position wins" instead of list-order-with-comparison-skip. Re-verifying that version against the FULL live dataset (not just the 7 target postings) before finalizing caught 10 NEW regressions it would have introduced: 10 unrelated postings (5666-5669, 6867, 12995-12998, 13001) whose description states a generic "Vergütung nach AVR" EARLIER in the text and the real, specific "AVR-Caritas" LATER -- pure position-based selection would have downgraded these from the correct specific "AVR Caritas" to the vaguer "AVR (unspecified)", a net loss of information with no traegerart-mismatch upside (both traegerart-consistent before and after). Caught this by re-running the fix against the entire 1340-row live set before treating any version as final, not just the 7 cases it was designed for -- switched to the comparison-marker-aware, list-order-preserving version instead, which was then re-verified to change EXACTLY the 7 target postings (all become traegerart-consistent) and zero others (aside from the 1 already-explained pipeline-staleness case, 10425, which is None either way regardless of algorithm).
