## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Crawler-review 2026-09-18, project rule "No safety nets" violations across the pipeline. Root pattern: crawlers/vendor_adapters.py get() (:71) swallows every transport exception into None, and every adapter converts that (and any non-2xx) into an empty return; app/crawl.py _fetch_board (:644/:646/:655) then reports err=None for a board that yielded 0 rows/observations without raising -- so it skips the 3-attempt retry ladder and never reaches crawl_issues (the daily error report). Measured on the last full adapter run (run 89, 2026-09-17): 18 of 216 boards (21 clinics, ~3303 beds) went silently zero -- Asklepios group (7 clinics), both Wertachkliniken, both Aschaffenburg-Alzenau sites, both Reisach sites, kh-as.de, kreisklinik-woerth.de, kh-nuernberger-land.de, pflegejobs.brk-... -- and crawl_issues has never once contained a kind=vendor row despite this. The same swallow pattern recurs at beesite.py:107 and hr4you.py:109 per-tenant, crawl_rexx (:1152), crawl_smartrecruiters (:296), _paginated_job_links (:736, used by wp_jobs/typo3_jobs/concludis/talention/oracle-fallback), and crawl_group_portal (:1482) -- each treats a failed page fetch as the boards own end-of-list signal. Separately, several self-invented caps silently truncate a board and return the partial result as a normal success with no truncated flag: find_job_urls sitemap-index walk (:468, locs[:3] + max_maps=8 -- confirmed biting on klinikum-ab-alz.de wp-sitemap.xml, dropping unnamed children 4-8), Crawler.sitemap_job_urls (career_crawl.py:233, 400-URL cap + 10-child index slice), _crawl_urls queue ceiling (career_crawl.py:288, len(seen_lists)+len(list_q) >= list_budget*2), the umantis list_pages=6 branch (app/crawl.py:339, below the seed own 7-8 start URLs, every umantis board permanently truncated=true), crawl_mein_check_in VENDOR_MAX_JOBS=300 default (vendor_adapters.py:1234, the last surviving instance of a cap already removed elsewhere), Crawler.crawl() section-first merge dropping the sub-walk truncated flag (career_crawl.py:352), app/crawl.py _verify_ids fallback [:200] (:772), and cmd_inbox --max-batches default 20 (cli.py:377). On top of the caps, run-level observability is broken: app/crawl.py status logic "done if not errors or n_rows" (:777) reports a run done even when the whole intake block (inbox post/drain/link-cross/verify) was skipped by an exception -- 6 historical runs (13,16,67,74,83,86) show n_new=0 with status=done; the return codes of both _cli(["inbox"]) and _cli(["link-cross"]) calls (:760/:767) are discarded outright. app/runs.py record_crawl_issue (:112) upserts on (board_url, day) only, so a board failure and that same days per-posting verify/city issue collide and the later write erases kind/vendor/clinic_ids -- confirmed erasing 883 of the days crawl_issues rows on 2026-09-17. coverage._last_run (app/coverage.py:130) matches any run that merely touches one of an adapters clinics, so the nightly verify run (399 clinics) wins for every one of the 18 adapter rows on GET /api/coverage and reports its run-wide totals identically across all of them, hiding the per-board zero-yield problem from the one surface meant to answer "is every board covered". See /tmp/crawler_review_2026-09-18.md sections "app/crawl.py", "app/runs.py", "app/coverage.py", "crawlers/vendor_adapters.py", "pflege_jobs/sources/career_crawl.py" for full evidence.

## Acceptance Criteria
