04Blockers

B1Dedup key both splits and merges wrongly
Break
1.46 hashes/URL splits one posting into many; merge-duplicates overwrites clinic_id, collector, run_id, first_seen_at
Cost
silent loss of which clinic/run observed a row, on every shared board
Fix
append-only. No unique constraint, hash as a plain index, Prefer: return=minimal. Dedupe in the query, never in the write.
B2mode=research silently degrades the live site
Break
app/runs.py:167 — last_run_per_clinic() selects any run in done/failed/running with no mode filter. Verified by reading it.
Chain
research run writes clinic_ids=[X] → coverage shows X crawled today → app/hunter.py:12 skips the real crawl → coverage decays, no error
Fix
research never calls execute(), writes clinic_ids=[]; add and mode != 'research'. Or skip HTTP mode entirely — a CLI has none of this.
B3Backfill rollback deletes live tee rows
Break
backfill posts run_id=null; rerun after the tee is live sets run_id=null on colliding tee rows; rollback is delete where run_id is null
Worse
raw_labels.raw_id FK makes that delete fail halfway, no transaction
Fix
falls out of B1 — append-only has no upsert, so nothing to collide
S1Research mode still reaches the network
Break
the guard patches requests.Session.request in-process. crawl.py:616-624 spawns python -m pflege_jobs.cli as a subprocess — fresh interpreter, no patch. Playwright (pi_asp, portals) never touches requests.
Worse
patching requests process-wide inside uvicorn also blocks concurrent live runs
Fix
research = read raw table, run pure functions, write labels. Nothing else. Then the guard has nothing to guard and gets deleted.
S2Region is injected, so geo evidence would be fake
Break
sources/inbox.py:43 writes region:"BAYERN" unconditionally; crawl.py:379 injects it too
Cost
any region-first labeller returns geo:region_exact → BY for 100% of the 2,396 live rows. The A/B that was supposed to prove the geo swap proves nothing.
Fix
trust region only from vendor payload, never from our own injection. Must land before the geo A/B, not after.

05Decisions I need from you

D1Dedup: how does a duplicate get removed?
Append-only, dedupe at query time
Nothing is ever overwritten, so "never remove" is true by construction. Costs ~3% extra rows (1.03/URL). Storage ≈ 230 MB/year at full Bavarian coverage.
unique(content_hash) + upsert
Smaller table, but measured at 1.46 hashes/URL it fails its own threshold, and every collision overwrites clinic/run attribution. ≈ 10 GB/year — past Supabase Pro's 8 GB inside a year.
D2Scope of the first build
Lazy version — 5 pieces, one day
Two tables · backfill 458 files + 7,279 inbox rows · 4-line tee behind a flag · geo module + dataset · one research CLI. Captures ~80% of the corpus because the vendor path (14k of 18k records) drops nothing inline.
Full 11-step plan
Adds drop_reason across 6 adapters, mode=research over HTTP, parallel workers, truncation logging in 8 files, harness graders. Every one carries a blocker or a YAGNI flag above.
D3The bite.py drop_reason refactor
Leave it alone for now
Replacing the continues at bite.py:310-317 triggers a detail-page fetch for every non-nursing posting and :318-320 forces in_bavaria=True and loses the tag on reassign — non-nursing rows would reach posting_observations. Live output changes.
Do it with the guard
Tag then out.append(o); continue before enrichment, plus and not o.get("drop_reason") at crawl.py:451. Recovers the seeded adapters' lost rows — but needs a per-family off/on diff to prove live output is byte-identical.
D4Remote research session
CLI only
python -m app.research --a live_v1 --b geo_v1. No B2, no S1, no run rows. Runs from any session over SSH.
POST /api/crawl mode=research
Nicer to trigger remotely, but needs the last_run_per_clinic fix first, and its rollback doesn't roll back — SQLite run rows outlive the revert.

10Engine design, its critique, backlog proposal

Fable designed the modular harvester you described; a second fable tore into it. Read the critique's blockers first — they are correct.

E1The ladder never escalates on the case it exists for
Break
run() treats zero rows with no error as success and stops. The 184 live boards / 15,603 beds are exactly "HTTP 200, 0 rows" — they would sit at last_result=ok, next_rung=null forever.
Fix
zero rows on a cheap rung = try the next cheap rung; stop only before expensive ones
E2Deleting ADAPTERS["umantis"] breaks 10 live clinics
Break
routing.py:126 marks any ats_type not in ADAPTERS as unroutable. 10 live rows are umantis (ANregiomed ×3, Klinikverbund Allgäu ×3, …). The entry is mislabelled, not dead.
Fix
change the value to ("seeded", "pflege_jobs.sources.ats_seeds:umantis"), keep the key
E3The vendor family is already raw-first — inbox keeps every row
Fact
sql/010 inbox has no unique constraint and no delete path; the drain acks with a note. client_id is free text → provenance today = client_id = "load:<n>", zero DDL.
So
postings_raw only adds value for page bodies — and your mirror requirement moves those to disk anyway
E4Three more: seeded wrapper, site_status rot, health SQL
Seeded
bite/softgarden/pi_asp return observations, need towns and their own sessions — app/crawl.py:304-363 _seed_obs is the real wrapper, 60 lines, reuse it
Status
site_status is written only by the new engine, never by execute() — two crawl paths, disjoint truth → make it a view over loads + incidents
Health
sum(distinct beds) collapses two 60-bed sites into 60 — and the metric is computable today from clinics + clinic_links + v_postings
