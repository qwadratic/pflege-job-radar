# WhatsApp — answering inbound Pflege leads

**What:** a candidate messages from a Meta ad on WhatsApp. Valentina replies, asks **one** question per message, and once the search is narrow enough names real open postings from exactly the data `GET /api/jobs` serves — clinic, city, link to the original ad.
**Where:** `app/wa/` (router `/api/wa/*`), state in `data/wa.sqlite`, unit `deploy/pflege-wa.service`.
**Status:** minimal harness. Answers inbound messages, prepares handoff to a human. Sends **nothing** to clinics, keeps every file a candidate sends ([Documents](#documents-inbound-media-originals-task-95); only `WA_BRAIN=luna` reads them and transcribes voice notes, [Voice notes](#voice-notes-task-107)), and without `WA_AUTOSEND=1` nothing reaches Meta at all — replies land as `draft` in the database.

Modeled on the production bot at `tasker-dispatcher-01` (`/opt/clinic-dispatcher/apps/connectors/`): same Meta Cloud API, same env names, same persona (internally "Luna", in-chat **Valentina von der NDT Group**, TASK-100), same style rule (short bubbles, one question per turn), same qualification bar (Urkunde / Defizitbescheid / passed Kenntnisprüfung). New here: questions come from live board data instead of a fixed script, and the deterministic branch below has no LLM call at all — testable, not just plausible.

## The conversation

No script — the harness fills **slots**, each slot a board filter:

| Slot | Filter in `GET /api/jobs` | Read from |
|---|---|---|
| `role` | `role_class` | "examinierte Krankenschwester", "OTA", "Stationsleitung" |
| `city` / `bezirk` | `city` / `regierungsbezirk` | town names the board actually knows |
| `department` | `department_hint` | "ITS", "OP", "Kreissaal" … (production bot's alias list) |
| `hours` | `employment_types` | "Vollzeit", "75%" |
| `housing` | `housing=1` | "brauche eine Wohnung" |
| `urkunde` | — | Urkunde, Defizitbescheid, Kenntnisprüfung; **not** a filter, the qualification bar itself |

**Data decides the next question.** For every open slot, `app/wa/brain.py:_gain` scores how much an answer would narrow the remaining rows: coverage × (1 − share of the most common value). "Intensiv or OP?" is useless when 90% of rows are already Intensiv; at 40/35/25 it halves the list. Highest-gain slot gets asked; below `MIN_GAIN`, the harness stops asking and just delivers.

So question order isn't fixed — it follows the live board. On real data (3625 open postings, 2026-09-11), city goes first: 406 postings are in München, so city narrows the most.

More rules, all in `app/wa/brain.py`:

- **Two bubbles, one question.** `_check()` raises if a turn has more — the style rule is an assertion, not a suggestion; it fails in tests, not in chat.
- **Numbers, not filler.** Every question carries the current count: "14 Stellen passen bisher."
- **Buttons from live data.** The three most common values become Meta reply buttons (max 3, titles ≤ 20 chars); free text always works too — typing "Stroke Unit" isn't limited to the suggestions.
- **One message can fill several slots.** "Intensiv in Würzburg, Teilzeit" fills three at once; none of those three get asked again.
- **Last statement wins.** "eigentlich lieber Augsburg" corrects the city. A bare "ja" answers only the question just asked — never one from four turns ago.
- **Nothing open isn't silence.** No posting matches → drop the loosest preference (housing → full/part-time → department → city) and **say so**: "Für OP in Augsburg, Vollzeit, mit Wohnung ist nichts offen – ohne Wohnungs-Wunsch: …". Still nothing → the harness says that plainly too.
- **No offer without recognition.** No Urkunde, Defizitbescheid, or passed Kenntnisprüfung → nobody gets introduced to a posting (same as the production constitution). "Not passed" is read even if nobody asked.
- **STOP means STOP.** "stop"/"stopp"/"abmelden"/"löschen" → `wa_threads.stopped`; nothing goes out after. The inbound message itself is still stored — it's the opt-out's own record. Whole-word match only, so "Stopfen"/"Intensivstation" don't fire.
- **Files.** A CV/Urkunde attachment is stored ([Documents](#documents-inbound-media-originals-task-95)) and acknowledged ("can't read this yet"), never silently swallowed — the deterministic branch reads nothing from it.

**What the rail costs, in seconds, because it changes how everything above it behaves.** One bubble owns the handset's flock for **90–150 s**: `open_chat` waits up to 12 s for the header, the pause after opening is up to 4 s, typing runs at the handset's own 3.2–5.5 chars/s (a 219-character reply measured at a median 56 s), then up to 30 s for the bubble to be drawn and up to 30 s for the tick. Consequences that are owned rather than hidden: the other lane on that phone logs `phone lock busy` for the duration; our own inbound watcher (lock timeout 5 s) counts a `busy_cycle` and skips, which is safe because the notification shade still holds the message; the client's read timeout is derived from the body length rather than fixed; and a multi-bubble turn waits out the fuse's published `next_slot_at` between bubbles instead of being refused 429 (TASK-146).

**The delivery column is ticks, not statuses, and the difference is the whole design.** The phone rail does report per-message delivery: the lane on that box scrapes the bubble's `status` content-desc — `'' | Gesendet | Zugestellt | Gelesen` — while it is still looking at the screen after pressing send. That is a real signal and this doc said "no" for a day, which was wrong. What it is *not* is a Meta status: there is **no webhook**, nothing arrives later, and a tick cannot be correlated after the fact because there is no message id to correlate it to. So it is readable exactly once, at send time, and a send whose tick could not be read is a **504**, never a `sent` (see the invariants below).

**Buttons are impossible on a phone rail, not unimplemented.** Reply buttons and list messages are Cloud API features; neither the consumer app nor the free WhatsApp Business app has any UI to *compose* one (its "quick replies" are typing shortcuts for the sender, not tappable elements for the recipient), so no accessibility service, adb macro or browser script can produce one. Every route is loopback-only and bearer-token guarded (`bridge/server.py:_guard`), and a refusal answers the same envelope shape everywhere: `{code, message, http_status, detail}` (`bridge/errors.py`).

`POST /v1/batches` is **not** built: a second pacing authority on the handset side needs a scheduler there, and until it exists a paced request is refused loudly with `429 rail_parked` and a `next_slot_at` the caller honours. Inbound is a **pull**, not a push, because an ingress tunnel into the VPS is not available — every leg is opened from our side over one `ssh -L`.

The `client_msg_id` we mint is the only id the message has, and the proof of delivery is the tick. A reply with no tick, or with the tick unreadable, is a **504** — `uncertain`, never auto-resent. A paced send answers **429 `rail_parked`** with a `next_slot_at`, which `campaign.py` files as `failed` with ownership restored and which a multi-bubble turn waits out rather than treats as an error (TASK-146). `bridge_sync` (TASK-125) is still unbuilt, so an `attempting` row has nothing that resolves it automatically — which is why every refusal where **nothing was typed** (a busy flock, a chat that would not open) has to leave no row at all, and does.

Inbound is Meta's own envelope on purpose: `parse_webhook_body` → `accept_payload` → `record_inbound_pending` and every `tests/test_wa_*.py` file stays valid unedited. If they need edits, the adapter is not thin enough. Errors raise `BridgeError(MetaError)` carrying an HTTP status (TASK-120), because `campaign.py:675-676` classifies 4xx as `failed` and anything else as `uncertain`, and `import_history.py:539` treats a `None` status as "no answer about this media" and aborts the import run — the two callers whose behaviour depends on that distinction.

**Transport-independent invariants.** These hold on both rails or the move is not allowed. One of them has two rail-specific forms, and the split is deliberate:

- **No `sent` without proof. The proof differs per rail, the refusal does not.** On the Meta rail the proof is a confirmed provider message id: `meta.py:560-563` raises when the API answers 2xx with no id — *"saying 'sent' here is the one lie that would corrupt the thread"* — and that code keeps its form, unchanged. On the phone rail there is no provider id to demand: the stack behind it has no message identifier of any kind, so the invariant is renegotiated (decision-8) to **no `sent` without a verified delivery tick**, read off the bubble at send time. A tick that could not be read is a 504 and stays `uncertain`; a status of **`unverified` must never become `sent`** — that is the exact failure the existing lane ships (it logs "treating as sent (unverified)" and records the send anyway, which fired on 2 of its 23 live sends), and refusing it at our boundary is half the reason we own this layer at all.
- **The id space is ours on this rail.** The `client_msg_id` we mint is the only id an outbound bridge message ever has. There is nothing to map back from the provider and nothing to correlate a tick to afterwards, which is why the tick is read synchronously or not at all, and why a mid-send crash reconciles by a tight body scan whose `indeterminate` verdict goes to a human rather than to a resend.
- **Turn-scoped deterministic idempotency keys** (TASK-114), and the reason is documented machinery, not caution: a raised send is recorded and re-raised (`api.py:1030-1031`), the claim is finished `skipped_error` (`api.py:906`), `store.py:372-375` documents that state as reclaimable, and `deploy/pflege-wa-catchup.timer` re-drives the turn 3 minutes later — the brain runs again and produces **new** bubbles. On the Cloud API the unconfirmed window is milliseconds; on a phone-mediated send it is 20-60 s and is the dominant failure class, so a random per-call key would deliver the same answer twice. The key is derived from the inbound id that already scopes the reply-turn claim — a Meta wamid on one rail, the inbound id *we* mint on the other — plus action and bubble index; campaign attempts key on `campaign_id|phone|attempt`. `bubble_index` is first-class rather than a detail: one bubble per call, so a turn whose second bubble fails never re-sends the first. First body for a key wins; a later different body replays the original result and sends nothing.
- **`wa_messages.wamid` UNIQUE** (`store.py:44`) stays the redelivery stop. Bridge inbound ids land in that same column, so a re-pushed inbound event is dropped exactly like a Meta redelivery — which only works if those ids are collision-free, and the existing lane's are not: it fingerprints on `sha1(direction|HH:MM|text)` with neither the phone nor the date in it, so two candidates answering "Ja" in the same minute collapse to one row and one of them is silently dropped. Ours keys on phone plus date plus occurrence index (TASK-131).
- **Opt-out detection.** Two detectors exist and only one survives the move: `slots.py:97 is_stop` reads the candidate's own text (`brain.py:332`, `luna_brain.py:1020` → `wa_threads.stopped`) and is transport-independent, but campaign-level `campaign.py:384 marketing_opt_out` reads Meta signals only — a `user_preferences` webhook and failed status code `131050` (`campaign.py:120`) — which a phone rail can never produce. TASK-113 (persistent suppression list) and TASK-137 (cross-lane, exported as salted digests) are therefore blocking before **any campaign on either rail**, not just on the bridge — two senders can now reach one candidate from one handset, and neither sees the other's traffic. Bridge-origin failures use our own `wab-*` slugs; a forged Meta numeric would be provenance forgery into a table whose reader documents itself as Meta's delivery status.

**Kill switch back to Meta, and its limit.** New threads: set `WA_TRANSPORT=meta` and restart — instant, which is why `META_WHATSAPP_*` stays configured permanently. Threads already answered from the phone number cannot silently follow: the rail is a different sender number. Inside the 24 h window such a thread would suddenly answer as the WABA number, a stranger to that candidate; past it `_send` routes to the reopen template (`api.py:979`) and raises when none is registered (`api.py:1034-1038`). Moving a live thread between rails needs an explicit, human-approved "number changed" message and is the only sanctioned way; other bridge threads stay parked on their rail. `GET /api/wa/health` reports the live transport (`config.py:201`), so which rail carries traffic is never guessed from `.env`.

### Handset operations as coded tools (TASK-147)

**Why they exist.** Ivan, 2026-09-21: the handset operations must be *code on the mini* that a model or an operator calls in one step — not an adb sequence somebody rewrites by hand every time. A script written in the moment has no identity check, no record and no verification: it taps where it expects the row to be and reports success because nothing raised. Six operations -- five single-chat ones plus the broadcast -- now carry that discipline in the operation itself, wherever the call comes from, and a seventh read reports the rail.

Deployed to the mini and restarted 2026-09-21 13:15 UTC; `GET /v1/health` carries the broadcast runner's heartbeat beside the watcher's, and `/v1/chats` refuses without the bearer token like every other route. | read thread | the bubbles WhatsApp draws **without scrolling** (`visibility: visible_without_scrolling`), oldest first, each with direction, clock, tick and body digest. Read-only | `wa_bridge.py read (--phone +49… \| --title "…") [--no-text]` |
| send one message | one bubble through `executor.send` — the same call the HTTP route makes, and deliberately too thin to bend its guarantees | `wa_bridge.py send --to +49… --body "…" [--key L] [--attempt N] [--dry-run]` |
| broadcast | one message to many recipients as a **ledger-backed run**, paced by the governor, resumable, stoppable | `wa_bridge.py broadcast --id RUN --file r.csv --body "…" [--send]`, then `--status` / `--stop` / `--runs` |
| clear chat | empty a conversation, keep it | `wa_bridge.py clear-chat (--phone … \| --title "…") [--confirm [--expect-messages N] [--keep-starred]]` |
| delete chat | remove the conversation from the handset | `wa_bridge.py delete-chat (--phone … \| --title "…") [--confirm [--expect-messages N]]` |
| report | every operation answers what it actually did: ticks for a send, per-item status for a run, `destroyed` + `verification` + `audit_id` for a destruction; `GET /v1/audit` is the standing record | `wa_bridge.py health [--json]` |

Run it on the VPS — the CLI talks to the executor through the same `ssh -L` the harness uses, so it needs both env files:

```bash
set -a; . ./.env; . /home/claude/.local/state/pflege-wa-bridge/rail.env; set +a   # WA_AUTOSEND; WA_BRIDGE_URL + WA_BRIDGE_TOKEN
```

Exit codes are the report: `0` done, `1` something needs attention (a refused or failed item, a bridge refusal, a destruction the executor could not verify), `2` usage or configuration error and **nothing was attempted**, `3` not finished (queued broadcast items — ask again with `--status`), `130` interrupted.

**The destructive discipline**, and every clause is there because its absence is a way to delete the wrong conversation:

1. **`confirm` is explicit.** No `confirm`, no taps — and the route names its arguments one by one rather than spreading the JSON body, so a hopeful `confirm_delete: true` is a loud unknown field instead of a silently ignored one (`server.py:_chat_args`).
2. **Read first, say what is about to go.** Without `--confirm` the CLI prints the row and the visible message count and destroys nothing. `--expect-messages N` then asserts that count: a conversation that grew a bubble since the preview is a different conversation from the approved one, and it is refused.
3. **Identity is proved, not assumed.** The row is matched again inside the executor; two rows with one title, or a display name the address book ties to two numbers, is a `409 chat_identity_mismatch`, never a coin toss. A caller that named a number gets the chat opened *by number*, which makes WhatsApp draw the header and the driver compare it before anything is tapped. A title the chat list does not show is `404 chat_not_found` — an error, not a no-op.
4. **One flock acquisition covers preview and act.** Releasing in between would let the other lane move the screen between what we looked at and what we tap, and that gap is the whole risk.
5. **The result is verified off the handset**: a cleared chat must be **still on the list** *and* read back empty, a deleted chat must be gone from a rescanned list. Both halves of the clear verdict matter — opening a number WhatsApp has no thread for draws an empty one, so "nought bubbles" alone cannot tell an emptied chat from a destroyed one, and `clear_chat`'s whole promise is that the conversation stays. An unverified destruction is a **504 `destruction_unverified`** — the same rule as `send_unconfirmed`: this rail does not report outcomes it has not seen. A driver failure *during* the verification (the chat list refusing to come to the front, adb dropping out) is that same 504, never a 500: the taps landed and the result is unproved.
6. **The audit row is written before the destructive verb**, not after it (`ledger.append_audit` → `ledger.finish_audit`), the same write-ahead shape as `ledger.begin` before the first keystroke of a send: everything between the tap and the answer is an adb call that can fail, and a conversation destroyed with no record is what this tool exists to prevent. The row carries operation, chat title, the number the *handset* says the chat belongs to, what was destroyed, and then the verification verdict; one still reading `state: attempted` is a destruction whose verification never ran. The retention sweep never touches that table.
7. **`archived` is the caller's assertion, never a field copied off the row.** Seven archived conversations are on that handset and nobody authorised touching them, so reaching one takes typing `--archived`; a row whose own `archived` disagrees with what was asserted is refused at both ends (`tools/wa_bridge.py::find_chat`, `operations.py::_match_row`) — the same shape as `--phone` disagreeing with the handset.

**A broadcast is a run, not a loop.** The items are written to the ledger before the first one is attempted (`create`), and `BroadcastRunner` — one item per cycle, 5 s poll — reads the ledger rather than a list, so it survives a restart of `pflege-wa-bridge.service` mid-run. Two independent things make the resume safe: a resolved item is no longer `queued`, and an item that died in the one window between the send and its status update is re-attempted with the **same deterministic `client_msg_id`**, where first-body-wins answers `replayed` and types nothing. Per-item statuses: `sent` (a verified tick, or a replay of one), `queued` (not attempted yet, or deferred until `next_attempt_at`), `refused` (refused before a key was pressed — waiting will not help), `failed` (the handset was touched and the outcome is not a tick, or a bug in the package raised while the item was being attempted — `code: executor_error`, and whether the handset was touched is exactly what is unknown; **never** retried automatically, for the same reason a 504 send is not). Every outcome, including an unclassified exception, is recorded **against the item it happened on** — `next_due_item` orders by run then position, so an item left `queued` after a bug would be handed back every poll and no other run would ever start — and `/v1/health`'s `runner.last_error` names the run and the item. One recipient's failure is one item's failure and the run continues. The hard stop is a flag in the ledger, not a variable in the runner, and it takes effect *between* items; a stop arriving after a run has finished leaves the finished run alone rather than rewriting a completed campaign as stopped — a stop can never interrupt a bubble mid-type, because an interrupted send is exactly the unconfirmable state this rail refuses to create.

**No new caps, and pacing stays where it was.** The governor is still the only pacing authority (`bridge/governor.py`: Europe/Berlin, active hours 09–20, Sundays blocked, first-touch gap 240–600 s, 10 first touches a day, 4 an hour, plus the per-number daily cap the server refuses to start without). A run's `--pacing` reaches it as `constraints` and may only make it **slower**. The constraint vocabulary is closed and checked at the boundary (`governor.CONSTRAINT_TYPES`: `min_gap_ms`, `daily_cap`, `first_touch_daily_cap`, `respect_quiet_hours`): an unknown key or a value the fuse cannot read as a number is a `400 invalid_request` naming it, at `create` time and before anything is stored — a `min_gap_sec` accepted and ignored is an operator who believes they asked for one message an hour. A `429 rail_parked` refusal carries a `next_slot_at`; the item stays `queued` until then. That is the whole scheduler — no retry ceiling, no maximum run size, no second fuse. `send` and `broadcast` are both paced as `first_touch`: an operator's message is not an answer to an inbound turn the harness is holding.

**Re-running a command is a replay, not a second message.** Every outbound key is minted deterministically on our side (`app/wa/bridge_ids.py`): `send` keys on `--key` (default: a digest of the body) plus recipient and `--attempt`; `broadcast` keys on `--id` plus each recipient and `--attempt` — the same minting a campaign attempt uses. To send the same text again on purpose, change `--key` or raise `--attempt`. Both commands need `WA_AUTOSEND=1`, the harness-wide switch the Meta rail already obeys; `broadcast` additionally plans and prints unless `--send` is given (the campaign CLI convention). A recipient file (`.csv` with a `phone` header, or `.json` list of objects, optional per-row `body`) is refused **whole** when any line fails to canonicalize or repeats a number: a broadcast that silently skips a recipient is one nobody can audit.

**First destructive use.** The three chats on the handset are test artefacts — Ivan's own test thread, the partner test contact, and an old soak-test thread with our own WABA number — and Ivan authorised their removal in writing on 2026-09-21 ("I authorise you, I insist, to delete this conversation"). They are the first conversations these tools destroy, through the tool and nothing else; the record of each is in `GET /v1/audit`.

**PLANNED, not built:** archived-folder handling beyond opening a row that is already archived; any scrolled (as opposed to visible) thread read; a broadcast whose bodies differ per recipient beyond the file's own `body` column; and `bridge_sync` (TASK-125), which is still what would resolve an `attempting` row without a human.

## Transport: the Meta rail

Meta WhatsApp Cloud API, Graph `v25.0`. Signature and challenge checks are lifted from the production client — they're the whole trust boundary.

| Route | Auth | What |
|---|---|---|
| `GET /api/wa/webhook` | Meta's `hub.verify_token` | handshake, echoes `hub.challenge` |
| `POST /api/wa/webhook` | `X-Hub-Signature-256` (HMAC-SHA256 over the raw body) | messages, statuses, every other webhook object; records, answers 200, turns run in the background |
| `POST /api/wa/route-webhook` | `X-Hub-Signature-256` | Meta's live webhook (nginx forwards the registered path here): split by owner, record ours, forward the rest (TASK-84, TASK-99) |
| `GET /api/wa/health` | public | readiness, no secrets; `stt_ready`/`stt_model` (TASK-107) |
| `GET /api/wa/threads` | owner session on 8501; none on 8502 (local-only) | threads with slots, `?phone=` for history + stored documents (metadata) |
| `GET /api/wa/ownership` | owner session on 8501; none on 8502 (local-only) | which system owns a phone's conversation (TASK-75) |

POST order, each step with its reason (TASK-99): read the body on the event loop, everything else in the threadpool → verify signature → compare `phone_number_id` (a change for a second number is stored raw, not answered) → record: `INSERT` on `wa_messages.wamid` (UNIQUE, so a Meta redelivery stops right here) plus a `wa_inbound_pending` row, statuses, raw events → queue the phones for the one background worker → 200. The worker, per message: arrival bookkeeping → media only: download and store the original (TASK-95); `WA_BRAIN=luna` document/image: read and classify it onto the card; `WA_BRAIN=luna` voice note: transcribe it (TASK-107) → save the thread (before any reply attempt) → claim and decide the reply → send → record the outbound, save the thread again (skipped when another process holds the claim) → delete the pending row. A turn failure no longer reaches Meta (no 502, no redelivery): it is logged, kept on the pending row and in `wa_send_failures`, and catch-up retries it. Details: [Webhook intake, background worker, recovery](#webhook-intake-background-worker-recovery-task-99).

`GET /api/wa/threads`/`GET /api/wa/ownership` are owner-only on the board process (`app/main.py`, `app/auth.py:OWNER_READ_PREFIXES`). The standalone `app/wa/asgi.py` (port 8502) installs no auth middleware, by decision (Ivan, 2026-09-14): it binds 127.0.0.1, nginx forwards only the webhook path to it, and it has no login route. Any local user on the harness host can read cards, messages and document metadata there — keep 8502 off any public nginx location.

## Documents (inbound media originals, TASK-95)

Every inbound `document`/`image`/`audio`/`video` message — both brains, stopped threads included — is downloaded (Meta's two-step media API) and stored **before** anything reads or answers it (`app/wa/api.py:_store_original`). A failed extraction, classification or transcription still leaves the file stored and linked; a failed download stores nothing. Either failure is recorded and catch-up retries it (TASK-99).

- **Where:** `WA_DOCUMENTS_DIR`, default `data/wa_documents/`. Layout `<dir>/<phone digits>/<UTC %Y%m%dT%H%M%S%f>Z-<media id alphanumerics><ext>`. The WhatsApp filename never names or places the file, extension included: `<ext>` is the mime type's (`_MIME_SUFFIX`), else `.bin` (TASK-95 review; `../../evil.sh` sent as `application/pdf` is stored as `.pdf`). Only the vision temp file takes a trailing 1–5 char alphanumeric extension from the filename, as a hint for the CLI's Read tool.
- **Write:** temp file in the same directory → fsync → `os.link` to the final name. Atomic, and an existing file raises `FileExistsError` instead of being overwritten (`os.replace` would overwrite). A Meta redelivery never gets this far (`wa_messages.wamid` drops it first), so `wa_documents.wamid` UNIQUE never blocks a first delivery.
- **Table `wa_documents`** in `data/wa.sqlite`, one row per stored file, index on `phone`:

| Column | Meaning |
|---|---|
| `id` | integer pk |
| `phone` | candidate `+E.164`, the link to `wa_threads`/`wa_messages` |
| `wamid` | inbound message the file came with (UNIQUE) |
| `media_id` | Meta media id |
| `kind` | `document`/`image`/`audio`/`video` |
| `mime_type` | from the webhook, else Meta's media lookup |
| `original_filename` | as WhatsApp sent it; data only, never part of `path` |
| `path` | absolute path of the stored original |
| `sha256`, `size_bytes` | of the stored bytes |
| `received_at` | UTC ISO timestamp |
| `text`, `text_key` | extracted text and the card key it went to, chosen by `document_type` (`cv_text`/`urkunde_text`, null for other types, TASK-96); `WA_BRAIN=luna` document/image only. A voice note's transcript: `text_key` `voice_transcript` (no card key, TASK-107). Else null |
| `document_type`, `certificate_level` | `classify_document()` result (TASK-81); same scope. `unreadable` (certificate level null, no text): the vision model found no legible text (`CV.NoReadableText`, its `NO_TEXT_FOUND`) |
| `import_source`, `import_ref`, `import_meta` | imported documents only (TASK-102): source label, the source's id for the file (UNIQUE together), JSON `{origin, source_system, old_class, old_type, sent_at, source_path, obtained: disk\|meta, source_sha256, sha256_verified, media_id}`; `wamid` is null |
| `reuse_state`, `reuse_decided_at` | imported documents only: `pending` → `confirmed`/`declined` by the candidate's answer (TASK-102) |

Helpers in `app/wa/store.py`: `record_document`, `set_document_text`, `set_document_classification`, `documents_for(c, phone)`. A media message's `wa_messages.meta` also carries `media_id`/`media_mime_type`/`media_filename`, so a failed download (no file, no row) can be re-fetched by hand while Meta still serves that media id. Card fields (TASK-96, `_ingest_media`): the extraction method still follows the file type (text layer vs vision), but the card key follows the **classification** — `lebenslauf` → `cv_text`; `urkunde`/`defizitbescheid` → `urkunde_text`; `auslaendisches_diplom`/`aufenthaltstitel`/`dienstplan`/`other` → neither (text stays on the row). Text is appended to the key (blank line between files), never replaced: a CV sent as two page photos keeps both pages, a Defizitbescheid stays when a helfer certificate follows (consent feeds only these two keys to `CV.analyse_candidate`). `document_type`/`certificate_level` = latest file. `documents` = one `{id, document_type, certificate_level}` per file (no text, no path — the card goes to the model); `_documents_just_received` = the same summaries since the last reply, popped by `luna_brain.turn()` into the payload field `documents_just_received` (a media turn has empty `latest_inbound`; this is how the model knows a file, even a wrong one, just arrived). The card is saved right after ingest, before the reply attempt, so a claude CLI or Meta failure does not lose it; catch-up retries from that card. Catch-up (`catchup.py`, TASK-99) never answers a luna document/image turn whose file is not on the card: while the webhook worker stores or reads it, the `media:<wamid>` claim is in flight and the phone is left to the worker (`claimed_elsewhere`); after a crash or a failed download/ingest, catch-up downloads the original again with the `media_id` in `wa_messages.meta`, or re-reads the stored original (checked against its `sha256`) and classifies it, saves the card, then replies.

`GET /api/wa/threads?phone=` returns `documents`: every column except `text`, and `imported_messages` (TASK-102). No file bytes; the text the brain uses is already on the card in `thread.slots`.

**PII.** Real CVs, certificates, photos, voice notes. Directories `0700`, files `0600`, `data/wa_documents/` gitignored — never commit it, never copy its contents into tests, docs or notes. Readers: the service's OS user (the webhook, the catch-up/follow-up timers). No `claude` CLI call can open them: Luna turns and classification run with `--tools ""` (no file tools); the vision call keeps Read/Glob/Grep but runs with cwd and `--add-dir` both set to a single-file temp dir, plus `--no-session-persistence` (`app/cv.py:VisionClient`). It used to inherit the service's cwd, the repo root, which holds `data/wa_documents/` (TASK-95 review). **No retention for a candidate's files:** they and their rows stay until removed by hand; `STOP` does not delete them. The one exception is a test number ([Test numbers](#test-numbers-task-109)), whose files, rows and session transcript are wiped nightly.

## Voice notes (TASK-107)

A `WA_BRAIN=luna` voice note is transcribed and Luna answers what the candidate said (Ivan, 2026-09-14: like the old system). Before, it got the flat `MEDIA_REPLY` and the thread waited for a human, so a campaign reply spoken as a voice note stalled.

- **What counts.** `audio` messages, and `document` messages whose stored original has an `audio/*` mime type (`api.is_voice_note`). Video keeps `MEDIA_REPLY` + `card._unread_media`; the deterministic brain transcribes nothing.
- **Old system.** `apps/connectors/candidate_audio_stt.py`: OpenAI transcription, `whisper-1`, `OPENAI_API_KEY`, no language (the model detects it), and the upload name's suffix rules. Same here, but no key-file fallback (key from env only) and no openai SDK.
- **Client** `app/wa/stt.py`: one multipart `POST https://api.openai.com/v1/audio/transcriptions` (`model`, `file`) over urllib, transport injectable like `meta.py`. Upload name `voice-note<suffix>`: the WhatsApp filename's extension when the endpoint accepts it (flac, m4a, mp3, mp4, mpeg, mpga, ogg, wav, webm), else the mime type's (the old map: `audio/ogg` → `.ogg`, `audio/mpeg` → `.mp3`, …), else `.ogg` (old rule: WhatsApp voice notes are ogg/opus). Meta also delivers `audio/aac` and `audio/amr`, which the endpoint does not list; they go up as `.ogg` like in the old system, and a refusal is a loud error. Only the extension of the untrusted filename is used.
- **Where it runs.** `api.finish_inbound` → `_store_and_read`, under the claim `media:<wamid>`, after the original is stored (TASK-95): from the bytes just downloaded, or from the stored original re-read and checked against its `sha256`. Stopped threads: stored, not transcribed. The card is not touched: no `documents` entry, no `_unread_media`.
- **Stored.** One commit (`store.set_voice_transcript`): `wa_documents.text` = transcript, `text_key` = `voice_transcript`; the inbound `wa_messages` row gets `body` = transcript (was empty; the old system's `body = COALESCE(body, transcript)`), so every reader of the message sees what was said: `GET /api/wa/threads?phone=` messages, the consent CV analysis chat history (`CV.analyse_candidate`), campaign `--status` last text, a `replies_to` quoting it, the dry run; `meta` gains `transcript`, `transcript_model`, `transcribed_at` (marks the body as a transcript; `kind` stays `audio`/`document`). A later attempt reuses the stored transcript: a brain or Meta failure after it never pays a second transcription.
- **Turn.** The transcript is the turn's text, so everything decided in code reads it like typed text: STOP, and the locked out-of-scope text on an ordinary thread (`_region_shortcut_applies`). Payload `voice_note: true` (from `meta.transcript`), `latest_inbound` = transcript, `reply_context.kind` = `audio`/`document`. Prompt VOICE NOTE: answer the content like a typed message, may thank for the voice message, never say it cannot be heard or ask to type it; a transcript can mishear names, towns and numbers, so an unclear or implausible fact is asked back, not recorded (the city filter is an exact match: a misheard town as `city` would empty the shortlist).
- **Failures.** No key (no request made), HTTP or network error, timeout (`WA_STT_TIMEOUT_SEC`), a reply without `text`, an empty transcript: `stt.TranscriptionError`, raised through the TASK-99 path. Nothing is sent (no `MEDIA_REPLY`), no model turn; the pending row keeps `last_error` (`inbound <wamid> not finished: TranscriptionError: ...`), `wa_send_failures` records it once per distinct error, `GET /api/wa/threads` shows `pending_inbound` and `last_send_error`, `stuck_reply` once older than `WA_STUCK_REPLY_HOURS`. Catch-up (every 3 min) transcribes the stored original again; no retry limit and no final state, also for an empty transcript (a silent or noise-only note costs a paid call every 3 minutes until a human acts; contrast `unreadable` images, TASK-96 review).
- **Health.** `GET /api/wa/health`: `checks.openai_api_key`, `stt_ready` (key set), `stt_model`. Key presence only: a wrong key shows up as the first HTTP 401 on a voice note.
- **Model.** Default `whisper-1`: the old system's model, the only one used on these candidates' voice notes. OpenAI's docs (checked 2026-09-15) list `gpt-transcribe` (July 2026, "recommended for general transcription", $0.0045/min vs $0.006/min for `whisper-1`), `gpt-4o-transcribe` and `gpt-4o-mini-transcribe` (model page: lower word error rate than the original Whisper models) and state no per-language figure; no German comparison was found and no key was available to compare on synthetic audio. Every model accepts the same request (`model` + `file`, JSON `text` reply), so `WA_STT_MODEL=gpt-transcribe` is a config change; compare with the live test below before switching.
- **Deploy.** No key in `.env` on 2026-09-15. `pflege-wa.service` runs old code (flat `MEDIA_REPLY`) until restarted; after a restart on this tree without `OPENAI_API_KEY`, every Luna voice note stays pending with the no-key error and gets no reply until the key is set. The catch-up timer already runs this tree (the live database held no audio message on 2026-09-15). Key added: restart the service so it reads `.env`, check `stt_ready`, run the live test.

## Test numbers (TASK-109)

The operator tests the live harness from their own WhatsApp number (Ivan's ends 8778). That thread is a real conversation in a real database: it was counted in reports like a candidate, a campaign template could land in the middle of a test, and yesterday's card (consent, documents, campaign context) decided today's test — TASK-90 wiped it by hand with SQL. Now the number is marked, and a nightly job wipes it.

**The flag** is `wa_threads.is_test` (+ `test_marked_at`), added by the same idempotent `alter table` migration as the TASK-102 columns. Only the CLI writes it — `store._update_thread` does not, so no card save can flip it:

```bash
python -m app.wa.luna.test_threads --mark +49…8778     # opens the thread if the number never wrote
python -m app.wa.luna.test_threads --list
python -m app.wa.luna.test_threads --unmark +49…8778   # ordinary thread again; not a wipe
```

The number is canonicalized first (`meta.canonicalize_phone`, ≥ 8 digits); anything else exits 2 and writes nothing.

**Where the flag shows and what it excludes:**

| Reader | With a test number |
|---|---|
| `GET /api/wa/threads` | `is_test`/`test_marked_at` per row, `test_threads` counts them among the returned rows (real candidates = `total - test_threads`); `?phone=` the same on the thread. Listed on purpose — this is where an operator checks which numbers are flagged |
| Campaign sender (`campaign.decide`) | `skip_test_number`, checked **before every other action**, so no `--retry-uncertain`/`--retry-delivery-failed` path gets past it either; dry run and `--send` alike, nothing is claimed and nothing is POSTed |
| `reporting.report_row` | `test: true` — any count built from these rows can drop it |
| `shadow_run.phones_owed_a_reply` | left out of the **report**; `--phones <number>` still reports it (`test: true` on the row). The same query drives catch-up's owed pass, which passes `include_test=True` — a marked thread is still answered there (review 2026-09-16: filtering the driver left the operator's own owed message unanswered forever) |
| `GET /api/wa/queue`, `…/mailing-list` | left out: that list is the handoff a human works from. The entry itself is still written when a test thread consents — the whole path stays exercised |
| `export_known_phones` | unaffected: it exports the operator's own external database, not our threads |

**Not excluded, deliberately:** the conversation. Webhook worker, catch-up, follow-up nudges, document intake, voice notes, consent and the queue build run exactly as for a real lead — that is what makes it a test.

**The nightly wipe** `app/wa/luna/purge_test_history.py`:


| the card: `slots`, `asked`, `matches_sent_at`, `turns`, `last_inbound_at`/`last_outbound_at`, `stopped` | |

- **Only a marked thread.** A phone named with `--phones` that is not marked is a reported problem and exit 1, never a wipe. A file is only ever unlinked when a `wa_documents` row of that phone names it **and** the path is inside `WA_DOCUMENTS_DIR`; a row pointing outside it fails that phone loudly and deletes nothing of it (imported documents are copies inside the tree — `import_history` stores them with `api._write_original` and keeps the source path in `import_meta`, so this never reaches the old system's files).
- **Retention.** `--older-than-hours 0` (default, Ivan 2026-09-16, re-confirmed 2026-09-21 — a 48-hour threshold was tried that day and Ivan cancelled it: the nightly wipe clears **everything**) wipes every test thread. The installed unit on `tasker-dispatcher-01` runs `--older-than-hours 0 --apply`. With `N > 0` a test thread whose last activity (its own messages, documents, last inbound/outbound — imported history is not activity) is younger than N hours is left **completely** alone: a card that outlives the messages it was built from is worse than a full wipe. A phone with a turn in flight (`ST.claim_in_flight`) is skipped the same way — the webhook worker or catch-up is holding that card right now. That check reads inside the wipe's own `begin immediate` transaction, so a turn claimed by another process a millisecond later cannot slip between the check and the deletes and then save the pre-wipe card back (review 2026-09-16).
- **A session the store does not have** is a reported problem (exit 1), not a silent skip: the card names a session id, its transcript is somewhere else, and the conversation stays readable on disk. Usual cause: `CLAUDE_CONFIG_DIR` is not the config the `claude` CLI runs the Luna turns with. The rest of that thread's wipe still runs.
- **Dry run is the default** and reads a read-only in-memory copy of the database (`shadow_run.db_copy`), so it cannot write a row even by accident, and it unlinks nothing. It reports exactly what `--apply` would delete, per phone.
- **Deploy:** `deploy/pflege-wa-purge-test.service` + `.timer` (daily 03:00 Europe/Berlin, `Persistent=true`), retention and schedule as arguments in the unit files, nothing about either in the code. Not installed by this repo — same convention as the other units (`docs/rollout-runbook.md` §9). `CLAUDE_CONFIG_DIR` must be the CLI config of the unit's `User=`, or the report shows 0 transcripts for a thread that has a session id.

Tests: `tests/test_wa_test_threads.py` (offline, tmp SQLite plus tmp document/session directories, fake Meta and model): mark/unmark and that a card save never flips the flag, marking a number that never wrote, a non-number refused, the flag and count on `GET /api/wa/threads`, campaign plan + `send_one` skip with every retry flag set and no attempt row, report/shadow/queue exclusion with the same thread still reported when asked by name, a test thread answered end to end through the webhook, the wipe (every table, the document file, its directory, the session transcript, the card; ownership and a `Stopp` handled as above), the dry run changing nothing, a non-test thread with documents in the same tree untouched (and named explicitly: problem, exit 1), an idempotent second wipe, retention, a turn in flight, the CLI's own summary and `--json`.

**Conversation ownership (TASK-75):** `app/wa/routing.py`. Deploy templates also now exist for the two other periodic jobs that previously had none: `deploy/pflege-wa-catchup.service`/`.timer` (TASK-78, every 3 minutes) and `deploy/pflege-wa-followups.service`/`.timer` (TASK-85, every 15 minutes, matching that feature's own shortest tier). None of the three are installed anywhere by this repo — matching `pflege-wa.service`'s own convention, going live is a deliberate human decision.

**Webhook router (TASK-84, TASK-99):** `app/wa/router.py`, `POST /api/wa/route-webhook`: the dispatch layer TASK-75 itself left out, and Meta's live webhook (nginx forwards the registered path to it). `route_webhook()` verifies the signature and splits a payload so every object lands in exactly one half, except call objects. Every message sender first gets its `route_decision()` (which records a new phone's owner); then messages (`from`), statuses (`recipient_id`), contacts and user preferences (`wa_id`) and message echoes (`to`) go to their phone's recorded owner. Call objects (`api.is_call_object`: `calls[]`, statuses with `type=call`, interactive `call_permission_reply`) always go to the real system, whoever owns the chat: this harness places and answers no calls, and the real system is the call bridge (its manager CRM places calls and reads the SDP answer from the `calls` webhook and `ACCEPTED` from the call status; a missed candidate call flags a manager there). A phone we own also keeps a raw copy in `wa_webhook_events` (review fix 2026-09-14: a CRM call to a campaign phone never connected). A message status of a wamid we do not hold on a phone we own stays ours (open question for Ivan: the real system's CRM messages to such a phone). Only a message decides a new phone: a status, call or contact for a phone with no ownership record goes to the real system and records nothing (the known-phones export lags; a status of the real system's outbound message to a new number must not hand that conversation to us). A status of one of our own outbound wamids is always ours; an item naming no phone, every other value key (`errors`, `history`, …), every other change field (template status, account updates, …), a change for another `phone_number_id` and any unknown entry shape go to the real system unchanged. Only the envelope (`object`, entry `id`/`time`, change `field`, `messaging_product`/`metadata`) is copied into both halves. The `'us'` half is recorded (`app.wa.api.accept_payload`) and queued for the background worker, then the `'them'` half is forwarded synchronously, reconstructed and re-signed with the shared Meta app secret, to `WA_REAL_SYSTEM_WEBHOOK_URL`. A failed forward (or no URL configured) answers 502 so Meta redelivers; the redelivered `'us'` part is duplicates by then. Mounted in both `app/wa/asgi.py` and `app/main.py`, same two-doors pattern as the main webhook route.

**Local-only internal receiver (TASK-86):** `POST /api/wa/internal-webhook`, gated by `WA_INTERNAL_WEBHOOK_ENABLED` (default off) plus a loopback-only origin check (`router._is_local_caller`) — no Meta signature check here at all. Built for an alternative architecture to TASK-84's split-and-forward: instead of this harness receiving Meta directly, the real production system stays Meta's primary webhook and would need its own small addition — a check of whether an inbound message's phone is already a known candidate, and, only for a genuinely new one, a same-host call to this endpoint — before or instead of its own normal processing for that phone. **That real-system-side addition is not part of this repo and is not built here**: it touches a separate, live production codebase serving real candidate traffic, owned by a different team, and needs that team's own explicit review and sign-off — including confirming who has authority over how new-lead data is routed, not just who has server access. This repo only builds and tests the receiving half.

## Webhook intake, background worker, recovery (TASK-99)

Every webhook route (`/api/wa/webhook`, `/api/wa/route-webhook`, `/api/wa/internal-webhook`) reads the body on the event loop and runs the rest in the threadpool. No turn runs inside a request, so a 7–26 s Luna turn never stalls `/api/wa/health`, a forward, or the nginx 60 s proxy timeout. The request records, then answers 200:

| Object | Stored in | Notes |
|---|---|---|
| message `parse_message` answers | `wa_messages` + `wa_inbound_pending` | one commit (`store.record_inbound_pending`); meta keeps every parsed field (`button_id`, `media_id`, …) so the message can be rebuilt from the row |
| message status (not `type=call`) | `wa_message_statuses` | one row per (`wamid`, `status`, Meta `timestamp`): `phone`, `errors`/`conversation`/`pricing` (JSON), `raw`. A first `failed` also writes `wa_send_failures`: `delivery failed for <wamid>: code <code> <title>: <details>`. Latest per wamid: highest timestamp, then last received (`latest_message_status`) |
| anything else for our phones or number | `wa_webhook_events` | `phone`, `field`, `kind`, `raw`: calls and call statuses (raw copies; the router forwards them), contacts, message types `parse_message` does not answer (e.g. `system`, `order`, call-permission replies), `errors`, `user_preferences`, echoes; on the direct webhook also template/account updates and changes for another `phone_number_id`. An identical object is stored once |

A Meta redelivery adds nothing: messages are duplicates, statuses and events are already stored.

**Worker.** One thread (`api.submit_accepted`, `ThreadPoolExecutor(max_workers=1)`, Meta client built in the request). Per phone, under `ST._lock`: `drain_pending` takes the pending messages oldest first through `finish_inbound`; consent queue builds (TASK-66) run after the lock. `finish_inbound` is safe to repeat:
- bookkeeping: `last_inbound_at` = the message's recorded time (never moved back), `turns` = inbound messages up to it;
- media: store / download again / re-read and classify, or transcribe (TASK-107), under the claim `media:<wamid>`; the card and the transcript are saved before that claim is released;
- media ack and reply: under the reply claim `<wamid>` (TASK-77).

A drain stops while any claim of the phone is in flight, so the worker and catch-up never run two turns for one phone. A message is done (pending row deleted) unless its status is `claimed_elsewhere` or `rate_limited`; `claimed_elsewhere` with the reply claim already `sent` counts as done. Pending rows are finished even on stopped threads (the media original is still stored).

**Failures.** A turn failure never reaches Meta, it already has its 200. The worker logs it, stores it on the pending row (`attempts`, `last_error`, `last_attempt_at`), writes `wa_send_failures` once per distinct error, releases a reply claim a brain failure left `in_progress`, and goes on with the next message. Only a failed forward to the real system answers non-2xx (502).

**Recovery** (`app/wa/luna/catchup.py`, timer every 3 min). Pass 1 drains every phone with pending rows through the same `finish_inbound`:
- media without a stored original is downloaded again with the `media_id` in `wa_messages.meta`;
- a stored original not on the luna card is re-read and classified; a file with no legible text is final (`document_type=unreadable`, on the card, counts for no gate, the reply turn runs and Luna asks for a clearer file), never re-read (review 2026-09-14: a selfie cost a vision call every 3 minutes and never got a reply); a failed vision or classification call is retried;
- a `WA_BRAIN=luna` voice note without a stored transcript is transcribed from the stored original (sha256 checked); a failed transcription (no key, API error, empty transcript) is retried on every pass ([Voice notes](#voice-notes-task-107));
- video and deterministic-brain media get their ack (`api._media_ack`). `MEDIA_REPLY` promises that a colleague looks at the file, so the card first records it for a human: `card._unread_media` gains `{wamid, kind, document_id, received_at}`, `card._escalated` is set (`_escalate_reason` when none). A declined Luna card gets no `MEDIA_REPLY`: the silence is recorded (`ST.NO_SEND_STATE`, action `declined_no_send`), the flag still set (review 2026-09-14: a voice note after the decline ack got `MEDIA_REPLY`, and nobody was flagged for any voice note). Nothing here reads a video; `WA_BRAIN=luna` voice notes are transcribed since TASK-107.

A process killed mid-turn leaves its pending row and at most one `in_progress` claim, which goes stale after `STALE_CLAIM_SECONDS` (300 s); then catch-up finishes the message. Pass 2 keeps the old owed-thread rule (last message inbound, not stopped) for messages without a pending row. A consent reached in catch-up builds its queue entry. A failed message is reported as `error`, and the run exits 1.

**Visibility.** `GET /api/wa/threads` rows with unread media carry `unread_media` (`card._unread_media`). Rows with unfinished messages carry `pending_inbound` (`count`, `oldest_recorded_at`, `last_error`, `last_attempt_at`); `stuck_reply` is also true once the oldest is older than `WA_STUCK_REPLY_HOURS`. `?phone=` adds `pending_inbound`, `message_statuses` (latest per wamid) and `webhook_events`.

**Deploy.** `pflege-wa.service` runs the code it loaded until restarted; the catch-up and follow-up timers start a new process per run and use the current tree at once. Tests: `tests/conftest.py` waits for the worker before a test's monkeypatches are undone, so no job ever runs against the real database or Meta.

## Second brain: same persona, same rules, Claude instead of ChatGPT

`WA_BRAIN=luna` switches to `app/wa/luna_brain.py` — same transport layer, same `data/wa.sqlite`, but the reply now comes from Claude instead of the question ladder above. Persona, qualification gate, region boundary (Bavaria only), and live-market logic are lifted from the production implementation (`app/wa/luna/VENDORED.md` lists exactly what was kept, generalized, or dropped). Company references were stripped at first; since TASK-100 (Ivan, 2026-09-14) Valentina names the company exactly as the old bot does: "Ich bin Valentina von der NDT Group." / "ein digitaler Assistent der NDT Group" (old code: `candidate_whatsapp_ad_leads` first touch, `candidate_locked_phrases.HONEST_AI_IDENTITY_DE`).

**Decided in code, never by the model:**

- **STOP** never reaches the model — same as the deterministic branch.
- **Not placeable** (Pflegehelfer, training with no recognition path, failed Kenntnisprüfung): the first decline is the locked German text (`app/wa/luna/prompts.py:REJECT_BODY_DE`), never the model's own phrasing — the source's own "process-exact wording the model must not rewrite" rule.
- **A named Bundesland outside Bavaria** triggers the locked decline (`OUT_OF_SCOPE_REGION_DE`) — the board has no data for other states. Typed text on an ordinary thread only (`_region_shortcut_applies`): on a thread with `card.campaign` or `card.declined` the model reads it (a decline such as "habe schon eine Stelle in Hessen", silence after a decline, a yes from someone living elsewhere; review 2026-09-14: the shortcut sent "käme Bayern für Sie infrage?" to decliners, and follow-ups then nudged them), and a location pin or contact card never triggers it.
- **A decline** (TASK-101): the model only flags it; the reply is the fixed `DECLINE_ACK_DE`, once, and the card is marked declined. Details in [Campaign replies, our outbound, declines](#campaign-replies-our-outbound-declines-task-100101).

Everything else — tone, which question comes next, how the market snapshot is phrased, when to escalate — is Claude's call, from state `app/wa/luna_brain.py` hands it: the card (`card`, the equivalent of the source's `card_patch`), a `requirement_scoreboard` (state, not a script), and a `market_snapshot` from the exact filters `GET /api/jobs` also uses (`app/wa/brain.py:jobs_for`) — no second data path. The thread itself is never handed over as text anymore — it lives in the session (next section).

**One Claude Code session per WhatsApp number, not a stateless call per turn.** On first contact, `app/wa/luna_brain.py:Client` starts `claude -p --session-id <uuid>` and keeps the UUID on the card (`card._session_id`); every later turn for that number calls `claude -p --resume <same uuid>`. The inbound WhatsApp message becomes the real `user` message of that session, exactly like an interactive chat — Claude sees prior turns from the session itself, not a hand-built thread field. What's still resent fresh every turn is only what can change independent of the conversation: current card state, the requirement scoreboard, and the market snapshot (new postings appear, old ones close) — Claude can't "remember" that, every turn needs it fresh. `--resume`/`--session-id` only find a session again if `claude` runs from the **same working directory** it started in — so every call runs with a fixed `cwd=WA_LUNA_SESSION_DIR` (`data/wa_luna_sessions/`, default), regardless of the FastAPI process's own cwd.

**Call shape: the `claude` CLI, not an Anthropic SDK key.** `app/wa/luna_brain.py:Client` runs `claude -p --restricted --output-format json --system-prompt "…"` (full-replacement system prompt, not appended; `--restricted` strips bash/code-execution/WebFetch, none of which a chat reply needs anyway) and sends the payload over stdin. Rides whatever Claude Code login already exists on the host — no separate `ANTHROPIC_API_KEY`. A missing binary, a timeout (`WA_LUNA_TIMEOUT_SEC`, default 120s — raised from 60 after TASK-68's end-to-end run produced a real `subprocess.TimeoutExpired` at 60s on an ordinary turn: the tool call (TASK-62) plus `effort=high` sometimes need more time than the reply alone), a non-JSON result, or a response missing required fields all raise loudly instead of inventing a message.

```bash
WA_BRAIN=luna                  # deterministic (default) | luna
WA_LUNA_MODEL=claude-sonnet-5  # any model `claude --model` accepts (claude-haiku-4-5 = cheaper/faster)
WA_LUNA_EFFORT=high            # low|medium|high|xhigh|max -- "high" since TASK-62: planning tool use is real reasoning work
```

**Model's own tools (TASK-62, TASK-110):** `app/wa/luna/tools_server.py` is a stdio MCP server; every tool is read-only and calls the same `D.filter_jobs`/`D.filter_clinics` functions as `app/wa/brain.py` and `GET /api/jobs`/`/api/clinics`, so a tool result and the harness's own shortlist can never disagree. Base of every posting query: open postings the verifier re-fetched (`verify=live`), newest first — the same base `slots.filters` builds for `market_snapshot`.

| tool | when |
|---|---|
| `search_postings(city, department, role_class, regierungsbezirk, housing, employment_type, q)` | the general search: the candidate named a place, department or region |
| `search_postings_with_housing(city, department, regierungsbezirk)` | they need a flat — the housing filter is already on |
| `list_clinics_with_housing(city, regierungsbezirk)` | "which clinics offer a flat", with the count per clinic |
| `list_cities_with_postings(department, housing, regierungsbezirk)` | which cities actually have postings for that, most first — real alternatives instead of a town from memory |
| `count_postings(city, department, role_class, regierungsbezirk, housing, employment_type)` | a number: postings, clinics, cities, and `with_housing` next to it (open there, and how many with a flat). **At least one filter**, else a `ToolError` pointing at `market_snapshot.open_jobs` (TASK-110 review: live runs burned ~2s a turn re-deriving that total with every parameter empty, and the prompt rule saying so did not hold across runs) |
| `get_posting(posting_id)`, `list_clinics(city, regierungsbezirk)` | one posting; clinics as such |
| `read_board_docs(topic)`, `board_api_get(path, query)` | the fallback, below |
| `get_clinic_contact(clinic_id)` | **not** in `MCP_TOOL_NAMES`: contacts are for the human handoff after consent (TASK-91) |

Why the preset tools exist (Ivan, 2026-09-16): the housing filter had been a `search_postings` parameter for a whole task and the model never once used it. A schema that names `housing: bool` and nothing else teaches nothing; a tool whose name is the candidate's need is picked. `search_postings(department=)` and every preset reading a department word go through one reader, `slots.read_department_pref`, same as `market_snapshot` (TASK-96 review: live, `department="Intensivstation"` returned 0 rows): several departments find postings in any of them, a flexible word filters nothing, a word the board has no department for raises an MCP `ToolError` naming the board departments (TASK-104; before, `[]` read as "nothing open"), and so does an `ambiguous` value ("alles außer OP"). On the webhook worker's turn (`finish_inbound`, `last_inbound_at` = the message's recorded time), the window is practically always open — the check mostly matters once the dry-run tool (`shadow_run.py`, TASK-72) or the catch-up driver (TASK-78) reaches an older, unanswered thread.

**Templates by ID, full parameters, rendered text (TASK-98):** `app/wa/meta.py`. **Stage/ball reporting and migration (TASK-71):** `app/wa/luna/reporting.py` provides `stage_for(card)` (new_lead → qualifying → documents_in (any `cv_text`/`urkunde_text`) → ready (every gate but consent, incl. both documents) → consented, or not_placeable; declined and already_placed first, TASK-101) and `ball_for(conn, phone)` (us/them/silent/none, from the last row in `wa_messages`; silent = the last inbound has a recorded no_send, TASK-101) — both pure derivations from fields that already exist, no new columns, purely for reporting (dry-run tool, migration). `app/wa/luna/migrate_candidates.py` idempotently imports real candidates into `wa_threads` from a generic JSON export (`--input`, only `phone` required), never directly from any specific external system (same restraint as `external_contacts.py`, TASK-69). A row with no valid phone number is reported, never silently skipped; a second run only fills in the card, never overwrites it.

**Dry-run tool (TASK-72):** `python -m app.wa.luna.shadow_run` — the same safeguard the real production team already runs for exactly this purpose (`wa_shadow_run.py` on tasker-dispatcher-01): "what would the reply be, without sending", always against a copy of the database, never the real one. `shadow_run.db_copy()` opens the source strictly read-only (SQLite URI `mode=ro` — refuses writes, and refuses to even create the file if missing) and backs it up via SQLite's own online-backup API into an in-memory copy; everything after that reads and writes only the copy. Looks at every thread where `reporting.ball_for() == "us"` (last message inbound, a reply still owed) — in this harness, a state a message only occupies briefly (the webhook's background worker answers within seconds); a thread stuck there in the real database means something failed mid-flight, exactly what this safe inspection tool is for.

One quirk specific to `WA_BRAIN=luna`: the card carries a real, resumable Claude Code session id (`_session_id`). A dry run that resumed that session with `--resume` would leave a real, permanent entry in the exact session the next real webhook call resumes from — an irreversible side effect on shared external state a report-only tool must never risk. `shadow_turn()` always strips `_session_id` before calling the brain, so every Luna reply here comes from a fresh, disposable session — the card itself (what actually drives gates and matching) stays fully real, only the session's own conversational memory is missing, so wording may read a bit colder than the real reply would. The per-thread result reports stage, action, bubbles, and the TASK-70 gate (`freeform`/`reopen_template`/`reopen_template_missing`/`no_send`/`stopped`) — never written, not to the copy, not to the original.

**Rate limit, dedup claim, catch-up, failure visibility (TASK-76/77/78/79):** a comparison against the real production system found four concrete gaps, closed here. `app/wa/config.py:WA_LUNA_MAX_CALLS_PER_HOUR` (default 20, 0 disables) caps Luna calls per candidate per hour — a backstop against a runaway loop, not a conversation throttle; hitting the cap doesn't lose the message, it gets picked up on the next catch-up pass. `app/wa/store.py:wa_reply_turn_claims` is a durable, cross-process claim per (phone, inbound wamid) — needed once two entry points (webhook and catch-up) could both try to answer the same unanswered message at once; an aborted or rejected claim is reclaimable, only an actually-sent (`sent`) claim or a recorded no_send (`skipped_no_send`, TASK-101) blocks for good. `app/wa/api.py:process_owed_turn` bundles claim, rate check, brain call, send, and claim completion into one pipeline used by both `finish_inbound` (webhook worker, TASK-99) and `app/wa/luna/catchup.py` (new, TASK-78 — the live counterpart to `shadow_run.py`: same owed-reply query, but a real send, not a dry run). A Meta failure is now durably recorded (`wa_send_failures`, `_send_and_record`) before the exception is re-raised, instead of vanishing without a trace, and `GET /api/wa/threads` shows `stuck_reply` per thread (ball on us longer than `WA_STUCK_REPLY_HOURS`, default 2h) and `last_send_error` — no invented Telegram/email channel, just a durable, discoverable signal.

**Proactive follow-up nudges (TASK-85):** `app/wa/luna/followups.py`, `python -m app.wa.luna.followups` — the real system re-engages a candidate who went silent at tiered intervals (15m/1h/4h); this harness only ever replied before this task. One campaign id is one template id (another id raises). Not visible here: with `--override-no-history-source`, the old system's records and Stopps of phones never imported before; a `user_preferences` webhook of a phone the old system owned (the router forwarded it); Meta itself still refuses delivery to a marketing opt-out (status `failed` 131050, then `skip_opted_out` for later campaigns). `already_placed`, `qualification_ok=false` and `prior_placement.placed` are shown (stage, card), not skipped.

**Send (`--send`, needs `WA_AUTOSEND=1`, token, phone number id).** Per phone, lead-file order:

1. history import `--apply` (skipped only with `--override-no-history-source`). Before the claim: its card merge refuses while any claim of the phone is in flight. An opt-out/decline record or Stopp ends the phone here (`skip_opted_out`/`skip_declined`, card declined).
2. One `BEGIN IMMEDIATE` transaction: the window checked again on the run's clock (the import can take minutes of document reads; closed → no claim, the phone waits for the next window start, `--no-wait` exits 3; review 2026-09-14: a template went out at 21:03), eligibility checked again, no claim in flight (else `deferred`, retried later in the run; only claims younger than `STALE_CLAIM_SECONDS` count), the phone's next attempt row in `wa_campaign_sends`, `in_progress`, with prior owner/reason/since, `wa_nudge_claims` `campaign:<id>:<attempt>`, reply-turn claim `campaign:<id>` (the webhook worker and catch-up leave the card alone until the send is recorded), `routing.flip_to_us_for_campaign` (reason `campaign:<id>`). Replies and statuses route to us from here.
3. `POST` the template (`send_template(definition=, params=)`).
4. Result, each in one transaction:

| Outcome | Attempt | Also |
|---|---|---|
| wamid | `sent` (wamid, `sent_at`) | `record_campaign_send`: thread, outbound row, `last_outbound_at`, `card.campaign` |
| HTTP 4xx | `failed` (`error`, `error_code` = Meta `error.code`, `error_payload`) | `wa_send_failures`; ownership restored (`routing.restore_after_campaign_failure`; no prior record = row deleted; `ownership_restore=changed` when another explicit write happened meanwhile) |
| network error, timeout, HTTP 5xx, 2xx without wamid | `uncertain` | `wa_send_failures`; ownership stays us |
| crash or Ctrl-C during the POST | stays `in_progress` | reported as `uncertain` by every later run |

Re-run = resume: `sent` skipped, `failed` claimed again (attempt n+1), `uncertain`/`in_progress` never resent without `--retry-uncertain`, `delivery_failed` never without `--retry-delivery-failed`. A retry keeps the owner recorded before the first flip. A 2xx accepted POST proves nothing about delivery (live 2026-09-14: accepted, then status `failed` 131042 unsettled payments): delivery is only in the status webhooks.

**Table `wa_campaign_sends`** (`store.CAMPAIGN_SCHEMA`, created by the sender's connection only, `store.ensure_campaign_schema`): one row per attempt, `campaign_id`+`phone`+`attempt` pk, `state`, `template_id/_name/_language`, `variables` (JSON params sent), `rendered_text`, `prior_owner/_reason/_since`, `ownership_restore`, `wamid` (UNIQUE), `error`, `error_code`, `error_payload`, `claimed_at`, `sent_at`, `finished_at`. The phone's claim is its latest attempt. Delivery is not copied: `wa_message_statuses` by wamid is the one record, per attempt.

#### Attempts and retry of an undelivered template (TASK-106)

Ivan 2026-09-14: a template Meta accepted and then reported `failed` (131042 unsettled payments, 131026, 131049) is resent in the same campaign by an explicit flag, not under a new campaign id (that split one campaign across ids and reports). Live 2026-09-14: 131042.

- **Attempts.** Every claim inserts attempt n+1; an earlier attempt keeps its wamid, `error`, `error_code`, `error_payload`, prior owner and `ownership_restore`, and its delivery status stays in `wa_message_statuses` under its wamid. `store.claim_campaign_send` checks the latest attempt: `failed` always claimable, `in_progress`/`uncertain` only with `retry_uncertain` (an `in_progress` one is finished `uncertain`, "no POST result recorded (the sending run stopped); superseded by attempt n"), `sent` only with `retry_delivery_failed` while the latest status of its wamid is `failed`; else it raises. `finish_campaign_send`/`reconcile_campaign_send` name the attempt (a late result of a superseded attempt raises instead of overwriting the new one); `--mark-sent` records the latest attempt only.
- **`--retry-delivery-failed`.** Without it `delivery_failed` is planned and never sent (unchanged). With it, a `delivery_failed` phone is `skip_stopped`, `skip_declined`, `skip_opted_out` (also a `failed` 131050 status), `skip_replied` (any inbound message since the campaign first claimed the phone), else `retry_delivery_failed`; then the history source (TASK-105) as for any send, the window, eligibility again in the claim transaction. No cap on attempts: each retry is the operator's run. Once any attempt went out (`sent`, delivered or not), a later `retry_failed` or `retry_uncertain` of the phone makes the same `skip_replied` check (review 2026-09-15: a retry rejected with HTTP 400 131042 was planned `retry_failed` next and posted on top of the candidate's conversation with Luna). A `retry_failed`/`retry_uncertain` with no attempt out yet is TASK-103 behaviour, no such check (open for Ivan).
- **Ownership.** A retry's flip finds the campaign's own flip and records the owner the previous attempt recorded (the owner before the first flip), so a retry Meta rejects (HTTP 4xx) restores the pre-campaign owner: nothing reached the candidate. An undelivered attempt leaves ownership with us, as before.
- **Card and Luna.** Each sent attempt goes through `record_campaign_send`: its own outbound row, `card.campaign` = the latest sent attempt, `last_outbound_at`. The undelivered attempt's row stays; its `failed` status keeps it out of `outbound_since_last_turn`, and `card.campaign` is left out of the payload while the latest sent attempt is undelivered (TASK-100). A reply's `replies_to` is the row its context names, so a tap on attempt 2 reads attempt 2. Reply-turn claim `campaign:<id>` per campaign, nudge claim `campaign:<id>:<attempt>` per attempt.
- **Pacing.** Every attempt counts against `--batch-size` per interval (each is a claim and a POST).
- **Migration.** A TASK-103 table (pk `campaign_id`+`phone`, column `attempts`) is rebuilt on the first sender connection (live or the read-only snapshot copy, whose file is never written): one `BEGIN IMMEDIATE` transaction, layout checked again under the lock, each row becomes `attempt` = its `attempts` (earlier attempts of such a row were overwritten then and are not recoverable), index recreated; idempotent. The live `data/wa.sqlite` had no `wa_campaign_sends` table on 2026-09-14.

**Pacing and window.** At most `--batch-size` claims (attempts) of the campaign within any `--batch-interval-min`, counted from `claimed_at` in the database (a restart keeps the pace; two runs of one campaign share it), only while the local hour of `--tz` is inside `--window`. Outside: waits for the next window start; batch full: waits for the interval; both logged. `--no-wait` exits 3 instead (`stopped: {reason: outside_window|batch_interval|turn_in_flight, next_at}`); a later run continues. Pacing is per campaign id. The progress line shows each phone's claim or send time, not the time the loop started.

**Status (`--status`).** Read-only copy. Per claimed phone the latest attempt (attempt, state, wamid, sync error, latest delivery status with Meta error code/title/details) and `attempts`: every attempt with the same fields, one printed line each. For an uncertain attempt: the statuses received since its claim whose wamid we never recorded, with Meta's pricing/conversation `category` (evidence it went out when it is the template's). Replies: the candidate's messages since the first attempt that may have reached them (`sent_at` of a sent attempt, `claimed_at` of an uncertain/in_progress one; a rejected attempt reached nobody, nor did a sent one whose latest status is `failed`: review 2026-09-15, a message written after an undelivered 131042 attempt counted as its reply), each matched to the attempt it answers (`matched`: `{wamid, at, kind, attempt, matched_by}`, `context` = its context names that attempt's wamid, else `time` = the latest attempt before it); count, first/last, last text, button taps with `tpl:` payload and attempt, whether one quotes a template (`to_the_template`), per attempt `replies: {count, by_context}`. `not_answering_an_attempt: {count, first_at, last_at}`: messages since the campaign first claimed the phone that answer no attempt (written after a rejected or undelivered one). Unread media since that first attempt (videos a colleague must look at; voice notes only from before TASK-107 or on the deterministic brain), stage, declined, stopped, opt-out, owner. Totals per phone (latest attempt): by state, delivery status, replied, `wrote_not_answering_an_attempt`, declined, unread media, stopped, opted out; across attempts: `attempts`, `retried` (phones with more than one), error codes (`send <code>`, `delivery <code>`).

**Report.** stdout plus JSON (`--report`, default `~/pflege-campaign-reports/<campaign>-<mode>-<UTC>.json`, dir 0700, file 0600: phone numbers and names), rewritten after each send. Exit: 0 done; 1 a send of this run needs attention (failed, uncertain, import error), or a dry-run/finished run whose plan holds a problem lead (invalid lead, variables, conflicting duplicate, uncertain, delivery failed); 2 configuration/access (template not approved, token, `WA_AUTOSEND`, no history source and no override, history source access); 3 `--no-wait` stopped before the list was done without a send problem in this run, problem leads of the plan still printed (repair 2026-09-14: they turned every stop into 1); 130 interrupted.

**Replies.** Router → owner us → background worker → Luna with `card.campaign`, the template in `outbound_since_last_turn`, button payload and `replies_to` (TASK-100). No button = decline ack once, then silence (TASK-101). Non-responders get nothing: follow-ups skip threads without an inbound after `card.campaign.sent_at`; catch-up only answers inbound messages.

## Deliberately missing

- **No LLM by default.** The question ladder above is deterministic so every rule has a test. `WA_BRAIN=luna` (above) switches to Claude when the full persona/conversation is needed.
- **No clinic-side action.** `handover_requested` is recorded on the thread but sends nothing; a human takes over. The harness promises the lead exactly that, nothing more.
- **No proactive messages beyond the one tiered follow-up nudge** (TASK-85: 15m/60m/240m, capped per streak, quiet-hours-gated as of TASK-92, dedup-claimed as of TASK-93 — see the Luna section above). The campaign template is a separate, operator-run sender ([Campaign sender](#campaign-sender-task-103)); non-responders get nothing further. No portfolio-wide wake scanning, no interview-window reminders — the harness only ever reacts to a candidate or to that one narrow nudge job, nothing scans across candidates deciding what to say next.
- **No clinic-submission/manager-CRM outbound dedupe** of the kind the production draft/preview/confirm flow needs where a human and the bot share one number — not applicable here, there is no shared-number human handoff.

One deliberate deviation from the production template, and it now differs per brain. The production template ships its match list **without** links ("keeps people from leaving the chat"). The **deterministic** brain includes the posting's own `source_url`, one per line (`brain.py:255`, `:266`), because a list a candidate cannot verify is worthless. The **`WA_BRAIN=luna`** brain sends no link at all, and that is structural rather than a rule: `luna/offer.py` keeps `source_url`/`external_url` out of the payload the model writes from (TASK-144), so the ban in `luna/prompts.py:271` cannot be talked past. TASK-150 (PLANNED) reopens the evidence question for **test threads only**: a footnote offering the original posting, and on request the clinic's own career-site URL, assembled in code and never by the model, with production threads unchanged.

## Persona tests against the real CLI

`tests/test_wa_luna_personas.py` (marker `llm`, excluded by `-m "not llm"` like `network`/`completeness`/`mutation` — every test really calls `claude`, costs real money, takes several seconds per turn) plays several fully-invented personas through the real Claude call. The personas themselves are invented — names, details, dialogue lines — but the **patterns** they exercise (qualification-path mix, conversation shape, typical edge cases) come from an anonymized read of two months of the reference implementation's real WhatsApp history: read, aggregated into archetype groups, then discarded — no real name, phone number, or verbatim quote appears in this file.

```bash
.venv/bin/python -m pytest -q -m llm tests/test_wa_luna_personas.py
```

**Fixture board for the tools too (TASK-96 repair round 2):** the CLI spawns the MCP tools server as a fresh process, so the test's `D._snap` never reached it: it read Supabase (401 without the service env), every `search_postings`/`list_clinics` call came back empty, and Luna said "Für München ... keine offene Stelle" two turns before the shortlist named Klinikum München. The persona and e2e `board` fixtures now call `tests/luna_fixture_tools_server.py:use_fixture_board`: it dumps the fixture board to JSON and swaps the generated `--mcp-config` server to `python -m tests.luna_fixture_tools_server` (loads that JSON into `D._snap`, then runs the real `tools_server` through its own `serve()`, so an llm run applies the same parent-counted vocabulary and writes the same readiness stamp a live turn does, TASK-110). The persona board also has one clinic row per city now, with `jobs_fresh`/`jobs_live` (`GET /api/cities`, which `board_api_get` serves, reads them). The close, Svetlana and city/housing gate tests fail on a bubble that names München and says `keine <0-2 words> Stelle/Job/Angebot`. With the board visible, Luna names clinics from tool results before the documents arrive, so the close test looks for its first clinic mention only from the first turn after the upload. Live 2026-09-14 after the change: all 17 persona tests passed; e2e 3/3 consented (6/6/7 turns), and mai's close named 3 clinics.

The first real run found two real bugs a fully-faked test suite couldn't have caught:

- **Salary question answered instead of deferred.** With no explicit rule, the model once quoted a concrete salary range ("zwischen ca. 3.400 und 4.200 € brutto") despite the harness having no reliable data source for that. Fixed with a new rule (`app/wa/luna/prompts.py:RULES`, "SALARY"): never state or estimate a number, always defer to clinic confirmation.
- **A silent turn without `no_send` crashed the harness.** A model turn came back with empty `bubbles: []` but without setting `no_send: true` — `_check()` expected at least one bubble and raised `AssertionError`. Fixed: an empty `bubbles` array now counts as "nothing to say" on its own, regardless of the `no_send` flag (`app/wa/luna_brain.py:turn`, regression test in `tests/test_wa_luna_brain.py`).

A third finding was hardening, not a logic bug: `--restricted` alone still allows file-reading tools (only command/code-execution/WebFetch are dropped), and the model once wrote a file-access attempt as prose ahead of its actual JSON reply. The call now also runs with `--tools ""` (every tool off), and parsing itself (`app/wa/luna_brain.py:_parse_reply_json`) additionally tries to cut the JSON object out of surrounding text before finally giving up.
