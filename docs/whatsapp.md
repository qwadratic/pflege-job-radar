# WhatsApp — answering inbound Pflege leads

**What:** a candidate messages from a Meta ad on WhatsApp. Valentina replies, asks **one** question per message, and once the search is narrow enough names real open postings from exactly the data `GET /api/jobs` serves — clinic, city, link to the original ad.
**Where:** `app/wa/` (router `/api/wa/*`), state in `data/wa.sqlite`, unit `deploy/pflege-wa.service`.
**Status:** minimal harness. Answers inbound messages, prepares handoff to a human. Sends **nothing** to clinics, keeps every file a candidate sends ([Documents](#documents-inbound-media-originals-task-95); only `WA_BRAIN=luna` reads them), and without `WA_AUTOSEND=1` nothing reaches Meta at all — replies land as `draft` in the database.

Modeled on the production bot at `tasker-dispatcher-01` (`/opt/clinic-dispatcher/apps/connectors/`): same Meta Cloud API, same env names, same persona (internally "Luna", in-chat **Valentina von der NDT Group**, TASK-100), same style rule (short bubbles, one question per turn), same qualification bar (Urkunde / Defizitbescheid / passed Kenntnisprüfung). New here: questions come from live board data instead of a fixed script, and the deterministic branch below has no LLM call at all — testable, not just plausible.

## The conversation

No script — the harness fills **slots**, each slot a board filter:

| Slot | Filter in `GET /api/jobs` | Read from |
|---|---|---|
| `role` | `role_class` | "examinierte Krankenschwester", "OTA", "Stationsleitung" |
| `city` / `bezirk` | `city` / `regierungsbezirk` | town names the board actually knows |
| `department` | `department_hint` | "ITS", "OP", "Kreissaal" … (production bot's alias list) |
| `hours` | `employment_types` | "Vollzeit", "75%" |
| `housing` | `housing=1` | "brauche eine Wohnung" |
| `urkunde` | — | Urkunde, Defizitbescheid, Kenntnisprüfung; **not** a filter, the qualification bar itself |

**Data decides the next question.** For every open slot, `app/wa/brain.py:_gain` scores how much an answer would narrow the remaining rows: coverage × (1 − share of the most common value). "Intensiv or OP?" is useless when 90% of rows are already Intensiv; at 40/35/25 it halves the list. Highest-gain slot gets asked; below `MIN_GAIN`, the harness stops asking and just delivers.

So question order isn't fixed — it follows the live board. On real data (3625 open postings, 2026-09-11), city goes first: 406 postings are in München, so city narrows the most.

More rules, all in `app/wa/brain.py`:

- **Two bubbles, one question.** `_check()` raises if a turn has more — the style rule is an assertion, not a suggestion; it fails in tests, not in chat.
- **Numbers, not filler.** Every question carries the current count: "14 Stellen passen bisher."
- **Buttons from live data.** The three most common values become Meta reply buttons (max 3, titles ≤ 20 chars); free text always works too — typing "Stroke Unit" isn't limited to the suggestions.
- **One message can fill several slots.** "Intensiv in Würzburg, Teilzeit" fills three at once; none of those three get asked again.
- **Last statement wins.** "eigentlich lieber Augsburg" corrects the city. A bare "ja" answers only the question just asked — never one from four turns ago.
- **Nothing open isn't silence.** No posting matches → drop the loosest preference (housing → full/part-time → department → city) and **say so**: "Für OP in Augsburg, Vollzeit, mit Wohnung ist nichts offen – ohne Wohnungs-Wunsch: …". Still nothing → the harness says that plainly too.
- **No offer without recognition.** No Urkunde, Defizitbescheid, or passed Kenntnisprüfung → nobody gets introduced to a posting (same as the production constitution). "Not passed" is read even if nobody asked.
- **STOP means STOP.** "stop"/"stopp"/"abmelden"/"löschen" → `wa_threads.stopped`; nothing goes out after. The inbound message itself is still stored — it's the opt-out's own record. Whole-word match only, so "Stopfen"/"Intensivstation" don't fire.
- **Files.** A CV/Urkunde attachment is stored ([Documents](#documents-inbound-media-originals-task-95)) and acknowledged ("can't read this yet"), never silently swallowed — the deterministic branch reads nothing from it.

## Transport

Meta WhatsApp Cloud API, Graph `v25.0`. Signature and challenge checks are lifted from the production client — they're the whole trust boundary.

| Route | Auth | What |
|---|---|---|
| `GET /api/wa/webhook` | Meta's `hub.verify_token` | handshake, echoes `hub.challenge` |
| `POST /api/wa/webhook` | `X-Hub-Signature-256` (HMAC-SHA256 over the raw body) | messages, statuses, every other webhook object; records, answers 200, turns run in the background |
| `POST /api/wa/route-webhook` | `X-Hub-Signature-256` | Meta's live webhook (nginx forwards the registered path here): split by owner, record ours, forward the rest (TASK-84, TASK-99) |
| `GET /api/wa/health` | public | readiness, no secrets |
| `GET /api/wa/threads` | owner session on 8501; none on 8502 (local-only) | threads with slots, `?phone=` for history + stored documents (metadata) |
| `GET /api/wa/ownership` | owner session on 8501; none on 8502 (local-only) | which system owns a phone's conversation (TASK-75) |

POST order, each step with its reason (TASK-99): read the body on the event loop, everything else in the threadpool → verify signature → compare `phone_number_id` (a change for a second number is stored raw, not answered) → record: `INSERT` on `wa_messages.wamid` (UNIQUE, so a Meta redelivery stops right here) plus a `wa_inbound_pending` row, statuses, raw events → queue the phones for the one background worker → 200. The worker, per message: arrival bookkeeping → media only: download and store the original (TASK-95); `WA_BRAIN=luna` document/image: read and classify it onto the card → save the thread (before any reply attempt) → claim and decide the reply → send → record the outbound, save the thread again (skipped when another process holds the claim) → delete the pending row. A turn failure no longer reaches Meta (no 502, no redelivery): it is logged, kept on the pending row and in `wa_send_failures`, and catch-up retries it. Details: [Webhook intake, background worker, recovery](#webhook-intake-background-worker-recovery-task-99).

`GET /api/wa/threads`/`GET /api/wa/ownership` are owner-only on the board process (`app/main.py`, `app/auth.py:OWNER_READ_PREFIXES`). The standalone `app/wa/asgi.py` (port 8502) installs no auth middleware, by decision (Ivan, 2026-09-14): it binds 127.0.0.1, nginx forwards only the webhook path to it, and it has no login route. Any local user on the harness host can read cards, messages and document metadata there — keep 8502 off any public nginx location.

## Documents (inbound media originals, TASK-95)

Every inbound `document`/`image`/`audio`/`video` message — both brains, stopped threads included — is downloaded (Meta's two-step media API) and stored **before** anything reads or answers it (`app/wa/api.py:_store_original`). A failed extraction or classification still leaves the file stored and linked; a failed download stores nothing. Either failure is recorded and catch-up retries it (TASK-99).

- **Where:** `WA_DOCUMENTS_DIR`, default `data/wa_documents/`. Layout `<dir>/<phone digits>/<UTC %Y%m%dT%H%M%S%f>Z-<media id alphanumerics><ext>`. The WhatsApp filename never names or places the file, extension included: `<ext>` is the mime type's (`_MIME_SUFFIX`), else `.bin` (TASK-95 review; `../../evil.sh` sent as `application/pdf` is stored as `.pdf`). Only the vision temp file takes a trailing 1–5 char alphanumeric extension from the filename, as a hint for the CLI's Read tool.
- **Write:** temp file in the same directory → fsync → `os.link` to the final name. Atomic, and an existing file raises `FileExistsError` instead of being overwritten (`os.replace` would overwrite). A Meta redelivery never gets this far (`wa_messages.wamid` drops it first), so `wa_documents.wamid` UNIQUE never blocks a first delivery.
- **Table `wa_documents`** in `data/wa.sqlite`, one row per stored file, index on `phone`:

| Column | Meaning |
|---|---|
| `id` | integer pk |
| `phone` | candidate `+E.164`, the link to `wa_threads`/`wa_messages` |
| `wamid` | inbound message the file came with (UNIQUE) |
| `media_id` | Meta media id |
| `kind` | `document`/`image`/`audio`/`video` |
| `mime_type` | from the webhook, else Meta's media lookup |
| `original_filename` | as WhatsApp sent it; data only, never part of `path` |
| `path` | absolute path of the stored original |
| `sha256`, `size_bytes` | of the stored bytes |
| `received_at` | UTC ISO timestamp |
| `text`, `text_key` | extracted text and the card key it went to, chosen by `document_type` (`cv_text`/`urkunde_text`, null for other types, TASK-96); `WA_BRAIN=luna` document/image only, else null |
| `document_type`, `certificate_level` | `classify_document()` result (TASK-81); same scope. `unreadable` (certificate level null, no text): the vision model found no legible text (`CV.NoReadableText`, its `NO_TEXT_FOUND`) |
| `import_source`, `import_ref`, `import_meta` | imported documents only (TASK-102): source label, the source's id for the file (UNIQUE together), JSON `{origin, source_system, old_class, old_type, sent_at, source_path, obtained: disk\|meta, source_sha256, sha256_verified, media_id}`; `wamid` is null |
| `reuse_state`, `reuse_decided_at` | imported documents only: `pending` → `confirmed`/`declined` by the candidate's answer (TASK-102) |

Helpers in `app/wa/store.py`: `record_document`, `set_document_text`, `set_document_classification`, `documents_for(c, phone)`. A media message's `wa_messages.meta` also carries `media_id`/`media_mime_type`/`media_filename`, so a failed download (no file, no row) can be re-fetched by hand while Meta still serves that media id. Card fields (TASK-96, `_ingest_media`): the extraction method still follows the file type (text layer vs vision), but the card key follows the **classification** — `lebenslauf` → `cv_text`; `urkunde`/`defizitbescheid` → `urkunde_text`; `auslaendisches_diplom`/`aufenthaltstitel`/`dienstplan`/`other` → neither (text stays on the row). Text is appended to the key (blank line between files), never replaced: a CV sent as two page photos keeps both pages, a Defizitbescheid stays when a helfer certificate follows (consent feeds only these two keys to `CV.analyse_candidate`). `document_type`/`certificate_level` = latest file. `documents` = one `{id, document_type, certificate_level}` per file (no text, no path — the card goes to the model); `_documents_just_received` = the same summaries since the last reply, popped by `luna_brain.turn()` into the payload field `documents_just_received` (a media turn has empty `latest_inbound`; this is how the model knows a file, even a wrong one, just arrived). The card is saved right after ingest, before the reply attempt, so a claude CLI or Meta failure does not lose it; catch-up retries from that card. Catch-up (`catchup.py`, TASK-99) never answers a luna document/image turn whose file is not on the card: while the webhook worker stores or reads it, the `media:<wamid>` claim is in flight and the phone is left to the worker (`claimed_elsewhere`); after a crash or a failed download/ingest, catch-up downloads the original again with the `media_id` in `wa_messages.meta`, or re-reads the stored original (checked against its `sha256`) and classifies it, saves the card, then replies.

`GET /api/wa/threads?phone=` returns `documents`: every column except `text`, and `imported_messages` (TASK-102). No file bytes; the text the brain uses is already on the card in `thread.slots`.

**PII.** Real CVs, certificates, photos, voice notes. Directories `0700`, files `0600`, `data/wa_documents/` gitignored — never commit it, never copy its contents into tests, docs or notes. Readers: the service's OS user (the webhook, the catch-up/follow-up timers). No `claude` CLI call can open them: Luna turns and classification run with `--tools ""` (no file tools); the vision call keeps Read/Glob/Grep but runs with cwd and `--add-dir` both set to a single-file temp dir, plus `--no-session-persistence` (`app/cv.py:VisionClient`). It used to inherit the service's cwd, the repo root, which holds `data/wa_documents/` (TASK-95 review). **No retention or deletion logic exists yet:** files and rows stay until removed by hand; `STOP` does not delete them.

## Operations

```bash
# Env (same names as the production bridge, so one Meta app covers both)
META_WHATSAPP_APP_SECRET=…        # required: webhook signature
META_WHATSAPP_VERIFY_TOKEN=…      # required: handshake
META_WHATSAPP_ACCESS_TOKEN=…      # required to send and to download inbound media (both brains)
META_WHATSAPP_PHONE_NUMBER_ID=…   # required to send, also filters foreign webhooks
WA_AUTOSEND=1                     # without this: everything is stored as draft only
WA_DOCUMENTS_DIR=…                # optional: inbound media originals, default data/wa_documents (TASK-95)

.venv/bin/uvicorn app.wa.asgi:app --port 8502      # own process (deploy/pflege-wa.service)
curl -s localhost:8502/api/wa/health
.venv/bin/python -m pytest -q tests/test_wa_harness.py
```

Register the webhook with Meta: `https://<host>/api/wa/webhook`, field `messages`, verify token as above.

Two doors, one implementation: `app/main.py` mounts the same router (port 8501) so the harness runs locally without a second process. In production, nginx points at **one** of them — the dedicated process, so a lead doesn't wait behind a crawl snapshot. Both write `data/wa.sqlite` (WAL); only whichever one receives webhooks actually writes.

**Conversation ownership (TASK-75):** `app/wa/routing.py`. Idea: route new leads to this harness, leave existing ones with the real production system, except when we reopen an old conversation ourselves via our own reopen template (TASK-70) — that one explicit event hands ownership over from then on. `route_decision(conn, phone)` returns `'us'`/`'them'`: once decided, it stays that way permanently (only `flip_to_us_on_reopen()`, wired into `app/wa/api.py:_send_reopen_template`, and the campaign sender's `flip_to_us_for_campaign()`/`restore_after_campaign_failure()`, TASK-103, may ever change it). For an undecided number, `_is_known_to_real_system()` checks whether the real system already knows it — a deliberately generic, `WA_REAL_SYSTEM_PHONES_FILE`-configured text-file check (same restraint as `external_contacts.py`, TASK-69: no concrete system named here). Unconfigured means a loud error, not a guess — being wrong in either direction has a real cost. Readable via `GET /api/wa/ownership` (owner-only, same PII class as `/api/wa/threads`).

**Known-phones export (TASK-87):** `app/wa/luna/export_known_phones.py`, `python -m app.wa.luna.export_known_phones --db <path> --query <sql> --out <path>` — the producer `WA_REAL_SYSTEM_PHONES_FILE` needed and never had. Fully generic, same restraint as `external_contacts.py`: the operator supplies the exact database path and SQL query for their own environment, this module has no opinion about what table or columns it selects from beyond "first column is a phone-like value." Opens the source strictly read-only (SQLite `mode=ro`, same pattern as `shadow_run.py`) and writes the output atomically (temp file + `os.replace()`), since a live webhook process reads this file concurrently and must never see a half-written one. A row that fails to canonicalize is reported, never silently dropped — same `MIN_PHONE_DIGITS` footgun guard as `migrate_candidates.py`. Deploy template: `deploy/known-phones-export.service`/`.timer` (hourly, `KNOWN_PHONES_SOURCE_DB`/`KNOWN_PHONES_SOURCE_QUERY` supplied by the operator in a git-ignored `EnvironmentFile`, never committed).

Deploy templates also now exist for the two other periodic jobs that previously had none: `deploy/pflege-wa-catchup.service`/`.timer` (TASK-78, every 3 minutes) and `deploy/pflege-wa-followups.service`/`.timer` (TASK-85, every 15 minutes, matching that feature's own shortest tier). None of the three are installed anywhere by this repo — matching `pflege-wa.service`'s own convention, going live is a deliberate human decision.

**Webhook router (TASK-84, TASK-99):** `app/wa/router.py`, `POST /api/wa/route-webhook`: the dispatch layer TASK-75 itself left out, and Meta's live webhook (nginx forwards the registered path to it). `route_webhook()` verifies the signature and splits a payload so every object lands in exactly one half, except call objects. Every message sender first gets its `route_decision()` (which records a new phone's owner); then messages (`from`), statuses (`recipient_id`), contacts and user preferences (`wa_id`) and message echoes (`to`) go to their phone's recorded owner. Call objects (`api.is_call_object`: `calls[]`, statuses with `type=call`, interactive `call_permission_reply`) always go to the real system, whoever owns the chat: this harness places and answers no calls, and the real system is the call bridge (its manager CRM places calls and reads the SDP answer from the `calls` webhook and `ACCEPTED` from the call status; a missed candidate call flags a manager there). A phone we own also keeps a raw copy in `wa_webhook_events` (review fix 2026-09-14: a CRM call to a campaign phone never connected). A message status of a wamid we do not hold on a phone we own stays ours (open question for Ivan: the real system's CRM messages to such a phone). Only a message decides a new phone: a status, call or contact for a phone with no ownership record goes to the real system and records nothing (the known-phones export lags; a status of the real system's outbound message to a new number must not hand that conversation to us). A status of one of our own outbound wamids is always ours; an item naming no phone, every other value key (`errors`, `history`, …), every other change field (template status, account updates, …), a change for another `phone_number_id` and any unknown entry shape go to the real system unchanged. Only the envelope (`object`, entry `id`/`time`, change `field`, `messaging_product`/`metadata`) is copied into both halves. The `'us'` half is recorded (`app.wa.api.accept_payload`) and queued for the background worker, then the `'them'` half is forwarded synchronously, reconstructed and re-signed with the shared Meta app secret, to `WA_REAL_SYSTEM_WEBHOOK_URL`. A failed forward (or no URL configured) answers 502 so Meta redelivers; the redelivered `'us'` part is duplicates by then. Mounted in both `app/wa/asgi.py` and `app/main.py`, same two-doors pattern as the main webhook route.

**Local-only internal receiver (TASK-86):** `POST /api/wa/internal-webhook`, gated by `WA_INTERNAL_WEBHOOK_ENABLED` (default off) plus a loopback-only origin check (`router._is_local_caller`) — no Meta signature check here at all. Built for an alternative architecture to TASK-84's split-and-forward: instead of this harness receiving Meta directly, the real production system stays Meta's primary webhook and would need its own small addition — a check of whether an inbound message's phone is already a known candidate, and, only for a genuinely new one, a same-host call to this endpoint — before or instead of its own normal processing for that phone. **That real-system-side addition is not part of this repo and is not built here**: it touches a separate, live production codebase serving real candidate traffic, owned by a different team, and needs that team's own explicit review and sign-off — including confirming who has authority over how new-lead data is routed, not just who has server access. This repo only builds and tests the receiving half.

## Webhook intake, background worker, recovery (TASK-99)

Every webhook route (`/api/wa/webhook`, `/api/wa/route-webhook`, `/api/wa/internal-webhook`) reads the body on the event loop and runs the rest in the threadpool. No turn runs inside a request, so a 7–26 s Luna turn never stalls `/api/wa/health`, a forward, or the nginx 60 s proxy timeout. The request records, then answers 200:

| Object | Stored in | Notes |
|---|---|---|
| message `parse_message` answers | `wa_messages` + `wa_inbound_pending` | one commit (`store.record_inbound_pending`); meta keeps every parsed field (`button_id`, `media_id`, …) so the message can be rebuilt from the row |
| message status (not `type=call`) | `wa_message_statuses` | one row per (`wamid`, `status`, Meta `timestamp`): `phone`, `errors`/`conversation`/`pricing` (JSON), `raw`. A first `failed` also writes `wa_send_failures`: `delivery failed for <wamid>: code <code> <title>: <details>`. Latest per wamid: highest timestamp, then last received (`latest_message_status`) |
| anything else for our phones or number | `wa_webhook_events` | `phone`, `field`, `kind`, `raw`: calls and call statuses (raw copies; the router forwards them), contacts, message types `parse_message` does not answer (e.g. `system`, `order`, call-permission replies), `errors`, `user_preferences`, echoes; on the direct webhook also template/account updates and changes for another `phone_number_id`. An identical object is stored once |

A Meta redelivery adds nothing: messages are duplicates, statuses and events are already stored.

**Worker.** One thread (`api.submit_accepted`, `ThreadPoolExecutor(max_workers=1)`, Meta client built in the request). Per phone, under `ST._lock`: `drain_pending` takes the pending messages oldest first through `finish_inbound`; consent queue builds (TASK-66) run after the lock. `finish_inbound` is safe to repeat:
- bookkeeping: `last_inbound_at` = the message's recorded time (never moved back), `turns` = inbound messages up to it;
- media: store / download again / re-read and classify under the claim `media:<wamid>`; the card is saved before that claim is released;
- media ack and reply: under the reply claim `<wamid>` (TASK-77).

A drain stops while any claim of the phone is in flight, so the worker and catch-up never run two turns for one phone. A message is done (pending row deleted) unless its status is `claimed_elsewhere` or `rate_limited`; `claimed_elsewhere` with the reply claim already `sent` counts as done. Pending rows are finished even on stopped threads (the media original is still stored).

**Failures.** A turn failure never reaches Meta, it already has its 200. The worker logs it, stores it on the pending row (`attempts`, `last_error`, `last_attempt_at`), writes `wa_send_failures` once per distinct error, releases a reply claim a brain failure left `in_progress`, and goes on with the next message. Only a failed forward to the real system answers non-2xx (502).

**Recovery** (`app/wa/luna/catchup.py`, timer every 3 min). Pass 1 drains every phone with pending rows through the same `finish_inbound`:
- media without a stored original is downloaded again with the `media_id` in `wa_messages.meta`;
- a stored original not on the luna card is re-read and classified; a file with no legible text is final (`document_type=unreadable`, on the card, counts for no gate, the reply turn runs and Luna asks for a clearer file), never re-read (review 2026-09-14: a selfie cost a vision call every 3 minutes and never got a reply); a failed vision or classification call is retried;
- audio/video and deterministic-brain media get their ack (`api._media_ack`). `MEDIA_REPLY` promises that a colleague looks at the file, so the card first records it for a human: `card._unread_media` gains `{wamid, kind, document_id, received_at}`, `card._escalated` is set (`_escalate_reason` when none). A declined Luna card gets no `MEDIA_REPLY`: the silence is recorded (`ST.NO_SEND_STATE`, action `declined_no_send`), the flag still set (review 2026-09-14: a voice note after the decline ack got `MEDIA_REPLY`, and nobody was flagged for any voice note). Nothing here transcribes audio/video.

A process killed mid-turn leaves its pending row and at most one `in_progress` claim, which goes stale after `STALE_CLAIM_SECONDS` (300 s); then catch-up finishes the message. Pass 2 keeps the old owed-thread rule (last message inbound, not stopped) for messages without a pending row. A consent reached in catch-up builds its queue entry. A failed message is reported as `error`, and the run exits 1.

**Visibility.** `GET /api/wa/threads` rows with unread media carry `unread_media` (`card._unread_media`). Rows with unfinished messages carry `pending_inbound` (`count`, `oldest_recorded_at`, `last_error`, `last_attempt_at`); `stuck_reply` is also true once the oldest is older than `WA_STUCK_REPLY_HOURS`. `?phone=` adds `pending_inbound`, `message_statuses` (latest per wamid) and `webhook_events`.

**Deploy.** `pflege-wa.service` runs the code it loaded until restarted; the catch-up and follow-up timers start a new process per run and use the current tree at once. Tests: `tests/conftest.py` waits for the worker before a test's monkeypatches are undone, so no job ever runs against the real database or Meta.

## Second brain: same persona, same rules, Claude instead of ChatGPT

`WA_BRAIN=luna` switches to `app/wa/luna_brain.py` — same transport layer, same `data/wa.sqlite`, but the reply now comes from Claude instead of the question ladder above. Persona, qualification gate, region boundary (Bavaria only), and live-market logic are lifted from the production implementation (`app/wa/luna/VENDORED.md` lists exactly what was kept, generalized, or dropped). Company references were stripped at first; since TASK-100 (Ivan, 2026-09-14) Valentina names the company exactly as the old bot does: "Ich bin Valentina von der NDT Group." / "ein digitaler Assistent der NDT Group" (old code: `candidate_whatsapp_ad_leads` first touch, `candidate_locked_phrases.HONEST_AI_IDENTITY_DE`).

**Decided in code, never by the model:**

- **STOP** never reaches the model — same as the deterministic branch.
- **Not placeable** (Pflegehelfer, training with no recognition path, failed Kenntnisprüfung): the first decline is the locked German text (`app/wa/luna/prompts.py:REJECT_BODY_DE`), never the model's own phrasing — the source's own "process-exact wording the model must not rewrite" rule.
- **A named Bundesland outside Bavaria** triggers the locked decline (`OUT_OF_SCOPE_REGION_DE`) — the board has no data for other states. Typed text on an ordinary thread only (`_region_shortcut_applies`): on a thread with `card.campaign` or `card.declined` the model reads it (a decline such as "habe schon eine Stelle in Hessen", silence after a decline, a yes from someone living elsewhere; review 2026-09-14: the shortcut sent "käme Bayern für Sie infrage?" to decliners, and follow-ups then nudged them), and a location pin or contact card never triggers it.
- **A decline** (TASK-101): the model only flags it; the reply is the fixed `DECLINE_ACK_DE`, once, and the card is marked declined. Details in [Campaign replies, our outbound, declines](#campaign-replies-our-outbound-declines-task-100101).

Everything else — tone, which question comes next, how the market snapshot is phrased, when to escalate — is Claude's call, from state `app/wa/luna_brain.py` hands it: the card (`card`, the equivalent of the source's `card_patch`), a `requirement_scoreboard` (state, not a script), and a `market_snapshot` from the exact filters `GET /api/jobs` also uses (`app/wa/brain.py:jobs_for`) — no second data path. The thread itself is never handed over as text anymore — it lives in the session (next section).

**One Claude Code session per WhatsApp number, not a stateless call per turn.** On first contact, `app/wa/luna_brain.py:Client` starts `claude -p --session-id <uuid>` and keeps the UUID on the card (`card._session_id`); every later turn for that number calls `claude -p --resume <same uuid>`. The inbound WhatsApp message becomes the real `user` message of that session, exactly like an interactive chat — Claude sees prior turns from the session itself, not a hand-built thread field. What's still resent fresh every turn is only what can change independent of the conversation: current card state, the requirement scoreboard, and the market snapshot (new postings appear, old ones close) — Claude can't "remember" that, every turn needs it fresh. `--resume`/`--session-id` only find a session again if `claude` runs from the **same working directory** it started in — so every call runs with a fixed `cwd=WA_LUNA_SESSION_DIR` (`data/wa_luna_sessions/`, default), regardless of the FastAPI process's own cwd.

**Call shape: the `claude` CLI, not an Anthropic SDK key.** `app/wa/luna_brain.py:Client` runs `claude -p --restricted --output-format json --system-prompt "…"` (full-replacement system prompt, not appended; `--restricted` strips bash/code-execution/WebFetch, none of which a chat reply needs anyway) and sends the payload over stdin. Rides whatever Claude Code login already exists on the host — no separate `ANTHROPIC_API_KEY`. A missing binary, a timeout (`WA_LUNA_TIMEOUT_SEC`, default 120s — raised from 60 after TASK-68's end-to-end run produced a real `subprocess.TimeoutExpired` at 60s on an ordinary turn: the tool call (TASK-62) plus `effort=high` sometimes need more time than the reply alone), a non-JSON result, or a response missing required fields all raise loudly instead of inventing a message.

```bash
WA_BRAIN=luna                  # deterministic (default) | luna
WA_LUNA_MODEL=claude-sonnet-5  # any model `claude --model` accepts (claude-haiku-4-5 = cheaper/faster)
WA_LUNA_EFFORT=high            # low|medium|high|xhigh|max -- "high" since TASK-62: planning tool use is real reasoning work
```

**Model's own tools (TASK-62, wired in):** `app/wa/luna/tools_server.py` is a small stdio MCP server with four read-only tools — `search_postings`, `get_posting`, `list_clinics`, `get_clinic_contact` — calling the same `D.filter_jobs`/`D.filter_clinics` functions as `app/wa/brain.py` and `GET /api/jobs`/`/api/clinics`. `search_postings(department=)` reads the model's word with `slots.read_department` first, same as `market_snapshot` (TASK-96 review: live, `department="Intensivstation"` returned 0 rows). `Client._live_reply` launches it via `--mcp-config`/`--strict-mcp-config`/`--allowedTools` (scoped to exactly these four names, form `mcp__jobs__<tool>` — confirmed live, undocumented anywhere official; the server name is model-visible, so it is a neutral word, not the repo name, TASK-100). `market_snapshot`/`requirement_scoreboard` still ride in every payload regardless: a tool call is an addition, not a replacement, and a failed call just falls back to existing snapshot reasoning (no retry mechanism — deliberately rejected, see below). The prompt (`prompts.py`, TOOLS rule) demands proactive use: the moment a candidate names a city/department/clinic the snapshot doesn't already show, a real tool call must happen — never a guess.

Two gotchas hit live while building this, relevant to any future change here:
1. The model initially wrote `"search_postings"` as the value of `action` in its JSON instead of actually calling the tool — the strict "return ONLY a JSON object" instruction got misread as banning any intermediate action. Fix: `OUTPUT_INSTRUCTION` now states explicitly that this only governs the *final* text, after any tool calls.
2. `--mcp-config`'s per-server `cwd` field is not honored by this CLI version's stdio launcher — the server inherits the outer `claude` process's cwd (`C.LUNA_SESSION_DIR`, not repo root), so `python -m app.wa.luna.tools_server` fails with `ModuleNotFoundError: No module named 'app'`. Fix: `env.PYTHONPATH` in the generated config forces correct module resolution regardless of actual cwd. Same reason the server also gets `WA_SQLITE_PATH`/`WA_LUNA_SESSION_DIR` passed as env vars — it does a fresh `app.wa.config` import in its own process, so a test's `monkeypatch` in the parent process never reaches it otherwise.

**Documents gate (TASK-91, TASK-96):** the close needs **both** documents actually received and classified — a verbal "ich habe die Urkunde" never counts. `requirement_scoreboard`: `cv_document` (a `lebenslauf` in `card.documents`), `qualification_document` (per `qualification_path`: `urkunde` → an `urkunde` not `certificate_level=helfer`; `defizit`/`kenntnispruefung` → such an `urkunde` or a `defizitbescheid`; no/other path → nothing counts), `documents` = satisfied only when both are. `urkunde` is the German licence only; a home-country diploma is `auslaendisches_diplom` and counts on no path (live, before that type existed: a Ukrainian and a Philippine nursing diploma came back `urkunde`/`fachkraft` and opened the gate). Reads only `card.documents`: a legacy/migrated card with `cv_text`/`urkunde_text` but no `documents` list stays open, no fallback — Luna asks for both again. `next_objective` names what is missing: both together in one ask, or the one still missing by name. A rejected qualification (`qualification=blocked`) replaces every `next_objective` with a not-placeable hint, no region/city/housing/document ask. `market_snapshot.shortlist` stays empty until `documents` is satisfied. Prompt (DOCUMENT ASK): the first ask names both (CV + Urkunde, or CV + Defizitbescheid on those paths), never "und/oder"; after that every Luna turn names the missing document again — also after a wrong document type, a bare "ja", or "schicke ich später". The consent recap mentions only documents in `card.documents`, never a claimed one. An imported document (`imported: true`, TASK-102) counts only with `reuse: confirmed`; while one is pending, `next_objective` asks the reuse yes/no instead ([Campaign recipients](#campaign-recipients-imported-history-reuse-of-earlier-documents-task-102)).

**Close sequence (TASK-63):** once qualification, and either city or department, and housing, and both documents (above) are all settled, `market_snapshot` also carries `matching_clinics_count` and `shortlist` (up to 5, populated only from that point). `department_pref` is the candidate's word; the filter reads it with the deterministic brain's alias list (`slots.read_department`: "Intensivstation"/"ITS" → `Intensiv/IMC`), a word the list does not know filters as written (TASK-96 review: the exact match left "Intensivstation" with an empty shortlist, and consent was asked with no clinic named; "egal" still filters to nothing). The prompt requires two separate turns (TASK-90): (1) total count plus shortlist, info only; (2) a one-line recap of the matched criteria plus the anonymized-send consent question (buttons, `anonymous_send_consent`). A later turn may re-mention an already-named clinic (e.g. inside the consent question itself) — only naming a clinic for the *first* time in the same turn that also asks for consent is forbidden.

**Consent scope covers matching clinics generally, not one named clinic (TASK-83):** the shortlist can legitimately have just one entry (a narrow market), which used to make the consent question read as "may I forward your profile to Klinikum X" — but `build_queue_entry` always matches against the *whole* live clinic snapshot (up to 5 results), not just what got named out loud. The prompt now requires the consent question to be phrased generally ("an bayerische Kliniken, die zu Ihrem Profil passen" / "to Bavarian clinics matching your profile"), never tied to one clinic's name, so what the candidate agrees to actually matches what the system does next.

**Post-consent queue (TASK-66):** the moment `anonymous_send_consent` flips to `true` on a turn, `app/wa/api.py` — only AFTER the thread is saved and AFTER the per-message lock (`ST._lock`) is released, so a matching run never blocks every other thread — builds a real entry via `app/wa/queue.py:build_queue_entry`: `app.autopilot.matching.rank()` (same transparent scoring engine, without writing real candidate PII into `app/autopilot`'s own, explicitly-synthetic demo database) ranks the candidate against every clinic in the live snapshot; a known contact (TASK-64/69) is attached where available. Two new, dedicated tables (`wa_queue_candidates`, `wa_queue_matches`, same sqlite file as `app/wa/store.py`) are idempotent (upsert) — a repeat consent duplicates nothing. `GET /api/wa/queue` (candidates × matching clinics) and `GET /api/wa/queue/mailing-list` (flat preview: candidate × clinic × contact email) are owner-only like `GET /api/wa/threads` — both send nothing, they're a report for a human to act on.

**Optional external contact-CRM source (TASK-69, extends TASK-64):** an operator can plug in their own, separately-maintained clinic contact CRM (human- or agent-maintained contacts, ideally with a source/evidence per entry) — `app/wa/luna/external_contacts.py` is a no-op unless `WA_EXTERNAL_CONTACT_DB` is set. When configured, it queries the given sqlite file read-only (reader command via `WA_EXTERNAL_CONTACT_READER`, default `sudo sqlite3`, since such a CRM file often has tighter permissions than this process itself), fuzzy-matches the clinic name (rapidfuzz, scoped to `bundesland='Bayern'`), and prefers a person with `role_category` `pflege_leadership`/`hr_leadership`/`hr` (expected schema: `companies`/`people`/`contact_channels`, see the module for details). `contacts.discover_contact` tries this source first, before `enr_contact_emails`/website/JD-rescan, and falls through on any failure (not configured, no read access, etc.) exactly as forgivingly as the existing website source always has.

**24h window and reopen template (TASK-70):** WhatsApp's own rule, not ours — plain free text only goes out within `WA_FREEFORM_WINDOW_HOURS` (default 24) of the candidate's last message; after that Meta rejects free text. `app/wa/api.py:_send` checks this in code, never the model: window closed → a pre-approved Meta template goes out instead of the bubbles (`Client.send_template`, `WA_REOPEN_TEMPLATE_NAME`/`WA_REOPEN_TEMPLATE_LANG`). No template configured → raises loudly, instead of attempting free text (which Meta would reject anyway) or silently doing nothing. A thread whose candidate never wrote (`last_inbound_at` unset, e.g. a campaign recipient who did not reply) has no window at all: `_freeform_window_open` is False (TASK-101; it used to be True). Every reply path sets `last_inbound_at` before it sends (`finish_inbound` → `_note_arrival`), so only a proactive send can hit this, and follow-ups skip such threads. On the webhook worker's turn (`finish_inbound`, `last_inbound_at` = the message's recorded time), the window is practically always open — the check mostly matters once the dry-run tool (`shadow_run.py`, TASK-72) or the catch-up driver (TASK-78) reaches an older, unanswered thread.

**Templates by ID, full parameters, rendered text (TASK-98):** `app/wa/meta.py`. Lookup is read-only: `Client.get_template(id)` = `GET /{id}?fields=id,name,language,status,category,sub_category,parameter_format,components`; `Client.find_template(waba_id, name, language)` lists with `name=` and matches exactly (Meta's `name` filter is a substring match, live 2026-09-14); none or several matches raise. `require_approved=True` raises unless `status` is `APPROVED`. `phone_number_info()` cannot resolve the WABA with this token (`#100 nonexisting field`), so use `META_WHATSAPP_WABA_ID`; its default fields are `display_phone_number,verified_name` (repair 2026-09-14: the old default asked for `whatsapp_business_account` and failed). Values go in one JSON mapping, bound against the definition (format in the comment above `TEMPLATE_FIELDS`): `header` (text variables, image/video/document `id` or `link`, location, product), `body` (list for POSITIONAL, mapping for POSITIONAL or NAMED; `currency`/`date_time` values), `buttons` by index (QUICK_REPLY `payload`, URL suffix variable, OTP `code`, COPY_CODE `coupon_code`, FLOW/CATALOG/MPM action, VOICE_CALL `ttl_minutes`/`payload`), `limited_time_offer`, `carousel` (one entry per card), `tap_target_configuration`. `validate_template_params` lists every missing, extra or invalid variable; `build_template_components`, `render_template` and `send_template(to, definition=, params=)` raise `TemplateParamsError` with that list before any POST. Unsupported: GIF headers (Marketing Messages API only) and component or button types not listed above (e.g. payments). These raise too. `render_template` returns `header`/`limited_time_offer`/`body`/`footer`/`buttons`/`carousel`/`call_permission_request`/`tap_target_configuration` plus `text`: the flat form for the stored outbound row, sections split by a blank line, media, location, buttons and cards as `[...]`. A QUICK_REPLY without a payload renders `payload: None`; Meta's button webhook then carries the label text as payload. URL variable values must already be percent-encoded, as Meta requires; they are rendered as given. The old call `send_template(to, name, lang, [body values])` is unchanged. Live 2026-09-14: all 29 WABA templates walk without unsupported types; `recruitment_job_wohnung_pflege_v2_de` (id `1061710426317037`) and `recruitment_bayern_stellen_interesse_de` (id `1791710088522158`) are APPROVED, POSITIONAL, text header, body `{{1}}`, two quick replies.

**Stage/ball reporting and migration (TASK-71):** `app/wa/luna/reporting.py` provides `stage_for(card)` (new_lead → qualifying → documents_in (any `cv_text`/`urkunde_text`) → ready (every gate but consent, incl. both documents) → consented, or not_placeable; declined and already_placed first, TASK-101) and `ball_for(conn, phone)` (us/them/silent/none, from the last row in `wa_messages`; silent = the last inbound has a recorded no_send, TASK-101) — both pure derivations from fields that already exist, no new columns, purely for reporting (dry-run tool, migration). `app/wa/luna/migrate_candidates.py` idempotently imports real candidates into `wa_threads` from a generic JSON export (`--input`, only `phone` required), never directly from any specific external system (same restraint as `external_contacts.py`, TASK-69). A row with no valid phone number is reported, never silently skipped; a second run only fills in the card, never overwrites it.

**Dry-run tool (TASK-72):** `python -m app.wa.luna.shadow_run` — the same safeguard the real production team already runs for exactly this purpose (`wa_shadow_run.py` on tasker-dispatcher-01): "what would the reply be, without sending", always against a copy of the database, never the real one. `shadow_run.db_copy()` opens the source strictly read-only (SQLite URI `mode=ro` — refuses writes, and refuses to even create the file if missing) and backs it up via SQLite's own online-backup API into an in-memory copy; everything after that reads and writes only the copy. Looks at every thread where `reporting.ball_for() == "us"` (last message inbound, a reply still owed) — in this harness, a state a message only occupies briefly (the webhook's background worker answers within seconds); a thread stuck there in the real database means something failed mid-flight, exactly what this safe inspection tool is for.

One quirk specific to `WA_BRAIN=luna`: the card carries a real, resumable Claude Code session id (`_session_id`). A dry run that resumed that session with `--resume` would leave a real, permanent entry in the exact session the next real webhook call resumes from — an irreversible side effect on shared external state a report-only tool must never risk. `shadow_turn()` always strips `_session_id` before calling the brain, so every Luna reply here comes from a fresh, disposable session — the card itself (what actually drives gates and matching) stays fully real, only the session's own conversational memory is missing, so wording may read a bit colder than the real reply would. The per-thread result reports stage, action, bubbles, and the TASK-70 gate (`freeform`/`reopen_template`/`reopen_template_missing`/`no_send`/`stopped`) — never written, not to the copy, not to the original.

**Rate limit, dedup claim, catch-up, failure visibility (TASK-76/77/78/79):** a comparison against the real production system found four concrete gaps, closed here. `app/wa/config.py:WA_LUNA_MAX_CALLS_PER_HOUR` (default 20, 0 disables) caps Luna calls per candidate per hour — a backstop against a runaway loop, not a conversation throttle; hitting the cap doesn't lose the message, it gets picked up on the next catch-up pass. `app/wa/store.py:wa_reply_turn_claims` is a durable, cross-process claim per (phone, inbound wamid) — needed once two entry points (webhook and catch-up) could both try to answer the same unanswered message at once; an aborted or rejected claim is reclaimable, only an actually-sent (`sent`) claim or a recorded no_send (`skipped_no_send`, TASK-101) blocks for good. `app/wa/api.py:process_owed_turn` bundles claim, rate check, brain call, send, and claim completion into one pipeline used by both `finish_inbound` (webhook worker, TASK-99) and `app/wa/luna/catchup.py` (new, TASK-78 — the live counterpart to `shadow_run.py`: same owed-reply query, but a real send, not a dry run). A Meta failure is now durably recorded (`wa_send_failures`, `_send_and_record`) before the exception is re-raised, instead of vanishing without a trace, and `GET /api/wa/threads` shows `stuck_reply` per thread (ball on us longer than `WA_STUCK_REPLY_HOURS`, default 2h) and `last_send_error` — no invented Telegram/email channel, just a durable, discoverable signal.

**Button-confirmed consent (TASK-80):** the real reference system already has a real button tap for its own harder clinic-submission gate, never inferred from free text — the same rigor now applies to the one consent point this harness has. `anonymous_send_consent` is never taken from the model's own `card_patch` anymore (also removed from `OUTPUT_SCHEMA`/`OUTPUT_INSTRUCTION`) — it's set exclusively from a real tap on one of two buttons (`consent:yes`/`consent:no`, `LB.CONSENT_BUTTONS`), the same "decided in code, not by the model" pattern as opt-out/reject/out-of-scope. Buttons attach exactly on the turn where `anonymous_send_offered` newly flips `true`; a new `is_button_reply` field in the model's payload lets Valentina honestly tell a real tap from typed text that merely sounds affirmative — in the second case she asks for the tap instead of claiming consent that doesn't exist yet.

**Document-type classification (TASK-81):** `app/cv.py:classify_document()` assigns an uploaded document a `document_type` (`urkunde`/`auslaendisches_diplom`/`lebenslauf`/`defizitbescheid`/`aufenthaltstitel`/`dienstplan`/`other` — the reference system's vocabulary plus `auslaendisches_diplom`, a nursing diploma/registration issued outside Germany, split from `urkunde` = the German licence in the TASK-96 review) and, for an Urkunde, a `certificate_level` (`fachkraft`/`helfer`/`unknown`) — explicitly distinguishing a real 3-year Fachkraft qualification from a Pflegehelfer/Pflegefachhelfer/Pflegefachassistent certificate (helper level despite the word "Fach"). Called directly at media intake (`_ingest_media`), lands on the card (and on the file's `wa_documents` row, TASK-95; since TASK-96 it also picks the card text key and feeds the documents gate) — no separate prompt wiring needed since `luna_brain._user_payload` already sends the whole card; a new rule in `prompts.py` just tells the model what the field means. Deliberately informational only: does not itself flip `qualification_ok` in code — out of this task's scope.

**Proactive follow-up nudges (TASK-85):** `app/wa/luna/followups.py`, `python -m app.wa.luna.followups` — the real system re-engages a candidate who went silent at tiered intervals (15m/1h/4h); this harness only ever replied before this task. Scaled-down equivalent: a thread is eligible once not stopped, not finished (`reporting.stage_for()` not `consented`/`not_placeable` — TASK-94; nor `declined`/`already_placed` — TASK-101; a finished thread always ends with our message), `reporting.ball_for()=='them'` (we already answered, no reply since; a recorded no_send is `silent`, not nudged), their last message is not unread media (`card._unread_media`: `MEDIA_REPLY` promised a colleague; review 2026-09-14: a voice-note reply to the campaign was nudged 20 minutes later), the candidate wrote at least once (`ST.has_inbound`, TASK-101: a campaign recipient who never replied gets nothing further) and after the latest `card.campaign.sent_at` (TASK-103: a recipient who wrote only before the template is a non-responder too), and enough time has passed since our last outbound to cross a tier not yet nudged in the current streak (default 15/60/240 minutes, `WA_FOLLOWUP_TIERS_MINUTES`) — capped per streak (`WA_MAX_FOLLOWUPS_PER_STREAK`, default 4, matching the real system's own cap). A reply resets the streak, derived from nudges sent since the candidate's own last message rather than a separate counter column. The nudge text is fixed and code-generated (`WA_FOLLOWUP_NUDGE_DE`), not a model call — an unprompted, system-initiated message is not what `luna_brain.turn()`'s "the candidate just said X" contract was built for, and a fixed, reviewable line is safer for something nobody asked the model to say. Sends go through the exact same `app.wa.api.send_and_record()` (renamed from `_send_and_record` once a second internal caller needed it) every other outbound path uses, so the TASK-70 24h-window/reopen-template gate applies here too. Two gaps closed after this landed: a quiet-hours window (TASK-92, `WA_QUIET_HOURS_START`/`_END`/`_TZ`, default 21:00–09:00 Europe/Berlin) skips the entire sweep rather than risk an unprompted 3am nudge — nothing is lost, the same tier fires on the next 15-min tick once outside the window; and a durable, cross-process dedup claim (TASK-93, `app/wa/store.py:wa_nudge_claims`/`claim_nudge`, same atomic-INSERT pattern as `wa_reply_turn_claims`) guards every send, generic enough for a future template-driven campaign to reuse directly, since `ST._lock` alone only serializes within one process.

**Still missing compared to the source:** no interview scheduling, no clinic-submission email flow, no manager-CRM handoff — same gaps as the deterministic branch (below), same reason: the infrastructure doesn't exist in this repo. An escalation (`escalate_to_manager`) is recorded on the thread (`_escalated`, `_escalate_reason`, readable via `GET /api/wa/threads`) but triggers no send of any kind.

### Campaign replies, our outbound, declines (TASK-100/101)

**Campaign contract.** One seed, `app/wa/store.py:record_campaign_send(c, phone, wamid, rendered, campaign_id, sent_at, template_id=, variables=, commit=)`, called by the sender ([Campaign sender](#campaign-sender-task-103)) after Meta returned the wamid, `rendered` = `meta.render_template(definition, params)` of exactly what was sent. One commit (`commit=False`: the caller's, with its claim): thread (created when missing), outbound row (`kind=template`, body = rendered text, `meta` = `{action: campaign, campaign_id, template_id, template, language, variables, buttons}`), `last_outbound_at` (never `last_inbound_at`), and on the card:

```
card.campaign = {campaign_id, template_name, language, rendered_text, buttons, sent_at, wamid}
```

A later campaign replaces `card.campaign`; every send stays a row. It does not check `stopped` or `declined` — the sender does before sending.

**Inbound parsing** (`api.parse_message`). A template quick-reply tap (`type=button`) keeps Meta's payload as `button_id = "tpl:<payload>"` (never equal to `consent:yes`/`consent:no` or a deterministic-brain id) and the label as text. Any message with `context` keeps it raw plus `reply_to_wamid = context.id` in `wa_messages.meta`. The deterministic brain reads a template tap as its label. Reactions, stickers, locations, contact cards and `unsupported` messages are answered like text from a summary (`api.SUMMARIZED_KINDS`; raw object kept in meta): a reaction's text is its emoji (`[reaction removed]` when empty) and its `reply_to_wamid` the message it is on, a sticker `[sticker]` (media id kept, not downloaded), a location `[location: name, address (lat, lon)]`, a contact card `[contact card: name phone]`, unsupported `[unsupported message]` (errors kept). They count as replies (`has_inbound`, campaign `--status`, follow-ups) and get a turn; prompt OTHER MESSAGE KINDS says how to read them (a 👍 on the template is a yes). Review 2026-09-14: a thumbs-up on the template was stored raw only, got no turn and counted as no reply. Other types (`system`, `order`, call-permission replies, …) stay raw in `wa_webhook_events`.

**Luna payload** (`luna_brain.turn_context`, passed by `api.process_owed_turn` and `shadow_run` on `t["turn_context"]`):

| Field | Meaning |
|---|---|
| `outbound_since_last_turn` | outbound rows since the model's last turn that the model did not write, oldest first: `{wamid, kind, text, at, action, template, delivery}` — campaign template, follow-up nudge (`action=followup`), decline ack, locked reject/out-of-scope text, a reopen template sent instead of the bubbles, manual sends. `delivery` = latest Meta status `{status, error_codes}` or null; a row whose latest status is `failed` is left out, and so is `card.campaign` from the payload card when its template failed (review 2026-09-14: a template undelivered with 131049 was presented as seen) |
| `last_turn_at` | when the model last answered (card marker) |
| `reply_context` | `{kind, received_at, is_template_button, template_button_payload, replies_to}`; `replies_to` = the stored row `context.id` names (outbound: with `delivery`), or `{wamid, found: false}` |
| `fresh_session` | no Claude session yet (no session memory) |
| `introduced` | a free-form outbound message already named Valentina or NDT Group or opened with "Hallo Frau/Herr" (`luna_brain.introduced`, the old bot's `_has_valentina_freeform_greeting`); templates, nudges and fixed acks do not count |
| `is_button_reply` | false for a template tap (it is not consent) |

Bookkeeping: card `_luna_last_turn = {at, seen_through_id, own_message_ids}`, written after the send; own rows = outbound rows after `seen_through_id` whose body is one of the model's bubbles and whose `meta.action` is the turn's action. A session from before the marker counts rows after its last `text`/`buttons`/`draft` row with an action not in `followup`/`media_ack`/`decline_ack`/`campaign`. A thread with no session sees every outbound row. `turn_context` raises when the turn key is not a stored inbound message.

**Prompt.** THINK ORDER 1: a thread opened by our template is not first contact (no welcome, no open-jobs opener, no region question). ### Campaign recipients: imported history, reuse of earlier documents (TASK-102)

Campaign recipients are old candidates of the previous system. Before the campaign, `app/wa/luna/import_history.py` imports what that system knows, so Luna does not re-ask it, and Luna asks before reusing an earlier CV/Urkunde (Ivan, 2026-09-14).

**Source contract.** No external schema in code (same as `export_known_phones.py`). The operator gives the source database (opened `mode=ro`), a label (`--source`, stored on every imported row), media roots for relative paths, and a queries file with four named queries (`-- query: facts|placement|messages|documents`), each bound to `:phone`/`:phone_digits`. Columns (NULL = unknown; a missing or unknown column raises):

| Query | Columns |
|---|---|
| `facts` | `source_ref`; `region`, `city`, `department_pref`, `qualification_path` (card vocabulary), `qualification_ok` 0/1, `urkunde_status`, `housing_known` 0/1, `people_count` > 0 |
| `placement` | `source_ref`; `clinic`, `status`, `stage`, `contract_start_date`, `updated_at`, `submitted` 0/1, `placed` 0/1 |
| `messages` | `source_ref`, `direction` in/out, `at`; `kind`, `body` |
| `documents` | `source_ref`, `origin` (`candidate` \| `forwarded` \| `derived_cv` \| `skip`); `path` (absolute or under a media root), `original_filename`, `mime_type`, `sha256`, `sent_at`, `old_class`, `old_type`, `media_id`, `source_system` |

`deploy/import-history.example.sql` is the set for the old system on this host, written from its code only: person records by `candidate_whatsapp_messages.phone_e164` and metadata phones; facts from `metadata_json.wa_agent.slots` (`pending_after_pruefung` → `kenntnispruefung`; `housing_known` only when true; no city slot there; a department only when `answers.departments` has exactly one); placement from `candidate_clinic_cases` (a row = submitted; `register_signed` or a contract start = placed) and `candidate_recruitment_state.placement_stage`; attachments by `source_system` (`meta_whatsapp_cloud`/`telegram_bot` → candidate, `owner_telegram*` → forwarded, `manager_crm_standardized_cv` → derived_cv, clinic packets, outbound media and anything unknown → skip), `crm_doc_class`/`crm_doc_type` kept as old class/type, `media_id` from the attachment or its message.

**Run.** Dry-run by default: reads the source, the files (sha256 checked) and our database read-only; writes nothing, no LLM, no Meta. `--apply` writes. Runbook step 6 has the command and the read grants. TASK-103 calls `import_phone(Source.open(...), phone, apply=True)` per phone. Report per phone: `found` (false: no query returned a row, nothing written, no thread created); facts known / imported / kept (card already has a value) / conflicting (two person records disagree: neither imported) / absent; placement records; messages found / imported; `stop_messages` (the candidate's messages that are a Stopp by `slots.is_stop`, `{source_ref, at, body}`; the campaign sender skips such phones); one action per document. CLI exit 1 when a document is not recoverable, 2 on an access error.

**What `--apply` writes.**
- Card facts into empty keys only.
- `card.prior_contact` = `{source, imported_at, first_contact_at, last_contact_at, last_inbound_at, last_outbound_at, messages_from_candidate, messages_to_candidate, facts_imported, documents_not_recoverable, summary}`; `summary` is a deterministic English paragraph (dates, counts, known facts, documents held, clinic record). `card.prior_placement` = `{records, submitted, placed}`.
- `wa_imported_messages` (one row per source message, UNIQUE `(import_source, import_ref)`), never `wa_messages`: those rows would count as turns and inbound, move the ball, open follow-ups and land in `outbound_since_last_turn`. A thread created by the import has no messages, `last_inbound_at` null, ball `none`.
- Documents, candidate/forwarded first, then derived CVs (imported only when no `lebenslauf` is held for the phone by then). Bytes from disk; a file missing on disk with a `media_id` is downloaded from Meta (GET only). Checked against the source sha256; an empty file, a mismatch, a missing file without `media_id` or a Meta HTTP refusal is `not_recoverable` (reported, listed on `prior_contact`). Same bytes already stored for the phone (e.g. re-sent on WhatsApp) → not stored again. Stored with `api._write_original` (0700/0600, no-overwrite), a `wa_documents` row with `import_*` and `reuse_state=pending`, then `api.read_and_classify` (the extraction and classification `_ingest_media` uses). Card entry `{id, document_type, certificate_level, imported: true, reuse: pending, sent_at}`; no `cv_text`/`urkunde_text`, no `_documents_just_received`.
- The card merge holds `ST._lock` and the claim `import:<source>`; a phone with any claim in flight raises (run again later).

Idempotent: source label + `source_ref` is written once; an imported file whose classification failed is re-read (sha256 checked) and classified on the next run; card entries are added only for ids not on the card. Loud failures: unreadable database, media root or file → `SourceAccessError` naming the path and the grant (the code never uses sudo); a Meta error without an HTTP status (no token, network) raises; a contract violation raises.

**Reuse question.** An imported `lebenslauf` or qualification document with `reuse: pending` counts for nothing. Declined: not counted, not offered again unless the candidate asks. A new upload confirms or declines nothing; it counts under the normal TASK-96 rules. `documents`, `prior_contact`, `prior_placement` are stripped from `card_patch`. **Send (`--send`, needs `WA_AUTOSEND=1`, token, phone number id).** Per phone, lead-file order:

1. history import `--apply` (optional). Before the claim: its card merge refuses while any claim of the phone is in flight.
2. One `BEGIN IMMEDIATE` transaction: the window checked again on the run's clock (the import can take minutes of document reads; closed → no claim, the phone waits for the next window start, `--no-wait` exits 3; review 2026-09-14: a template went out at 21:03), eligibility checked again, no claim in flight (else `deferred`, retried later in the run; only claims younger than `STALE_CLAIM_SECONDS` count), `wa_campaign_sends` row `in_progress` with prior owner/reason/since, `wa_nudge_claims` `campaign:<id>:<attempt>`, reply-turn claim `campaign:<id>` (the webhook worker and catch-up leave the card alone until the send is recorded), `routing.flip_to_us_for_campaign` (reason `campaign:<id>`). | Outcome | Claim | Also |
|---|---|---|
| wamid | `sent` (wamid, `sent_at`) | `record_campaign_send`: thread, outbound row, `last_outbound_at`, `card.campaign` |

- **No proactive messages beyond the one tiered follow-up nudge** (TASK-85: 15m/60m/240m, capped per streak, quiet-hours-gated as of TASK-92, dedup-claimed as of TASK-93 — see the Luna section above). The campaign template is a separate, operator-run sender ([Campaign sender](#campaign-sender-task-103)); non-responders get nothing further. No portfolio-wide wake scanning, no interview-window reminders — the harness only ever reacts to a candidate or to that one narrow nudge job, nothing scans across candidates deciding what to say next.
- **No clinic-submission/manager-CRM outbound dedupe** of the kind the production draft/preview/confirm flow needs where a human and the bot share one number — not applicable here, there is no shared-number human handoff.

One deliberate deviation from the production template: there, the match list ships **without** links ("keeps people from leaving the chat"). Here, `source_url` is included, because a list a candidate can't verify is worthless — and the board has no other outbound link anyway.

## Persona tests against the real CLI

`tests/test_wa_luna_personas.py` (marker `llm`, excluded by `-m "not llm"` like `network`/`completeness`/`mutation` — every test really calls `claude`, costs real money, takes several seconds per turn) plays several fully-invented personas through the real Claude call. The personas themselves are invented — names, details, dialogue lines — but the **patterns** they exercise (qualification-path mix, conversation shape, typical edge cases) come from an anonymized read of two months of the reference implementation's real WhatsApp history: read, aggregated into archetype groups, then discarded — no real name, phone number, or verbatim quote appears in this file.

```bash
.venv/bin/python -m pytest -q -m llm tests/test_wa_luna_personas.py
```

**Fixture board for the tools too (TASK-96 repair round 2):** the CLI spawns the MCP tools server as a fresh process, so the test's `D._snap` never reached it: it read Supabase (401 without the service env), every `search_postings`/`list_clinics` call came back empty, and Luna said "Für München ... keine offene Stelle" two turns before the shortlist named Klinikum München. The persona and e2e `board` fixtures now call `tests/luna_fixture_tools_server.py:use_fixture_board`: it dumps the fixture board to JSON and swaps the generated `--mcp-config` server to `python -m tests.luna_fixture_tools_server` (loads that JSON into `D._snap`, then runs the real `tools_server`). The persona board also has one clinic row per city now. The close, Svetlana and city/housing gate tests fail on a bubble that names München and says `keine <0-2 words> Stelle/Job/Angebot`. With the board visible, Luna names clinics from tool results before the documents arrive, so the close test looks for its first clinic mention only from the first turn after the upload. Live 2026-09-14 after the change: all 17 persona tests passed; e2e 3/3 consented (6/6/7 turns), and mai's close named 3 clinics.

The first real run found two real bugs a fully-faked test suite couldn't have caught:

- **Salary question answered instead of deferred.** With no explicit rule, the model once quoted a concrete salary range ("zwischen ca. 3.400 und 4.200 € brutto") despite the harness having no reliable data source for that. Fixed with a new rule (`app/wa/luna/prompts.py:RULES`, "SALARY"): never state or estimate a number, always defer to clinic confirmation.
- **A silent turn without `no_send` crashed the harness.** A model turn came back with empty `bubbles: []` but without setting `no_send: true` — `_check()` expected at least one bubble and raised `AssertionError`. Fixed: an empty `bubbles` array now counts as "nothing to say" on its own, regardless of the `no_send` flag (`app/wa/luna_brain.py:turn`, regression test in `tests/test_wa_luna_brain.py`).

A third finding was hardening, not a logic bug: `--restricted` alone still allows file-reading tools (only command/code-execution/WebFetch are dropped), and the model once wrote a file-access attempt as prose ahead of its actual JSON reply. The call now also runs with `--tools ""` (every tool off), and parsing itself (`app/wa/luna_brain.py:_parse_reply_json`) additionally tries to cut the JSON object out of surrounding text before finally giving up.

## End-to-end funnel test with two live agents (TASK-68)

`tests/test_wa_luna_e2e_funnel.py` (marker `llm`) goes one step further than the persona tests above: there, only Valentina is a real model call, the candidate script is deliberately fixed (stable for regression tests). ```bash
